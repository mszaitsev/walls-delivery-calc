# Walls Delivery Calc Documentation

Version: 0.139.6

0.137.3 narrows the Jet Logistic `calc_transport` currency interpretation after production diagnostics showed that `valuta` can be a Jet provider identifier while `valuta_name` carries the readable currency. The quote parser now uses `valuta_name` first, then textual `valuta` only when the name is absent, then the confirmed RUB Jet profile for missing or numeric provider codes. Explicit non-RUB readable currency still fails closed, and connection diagnostics show safe `valuta`/`valuta_name` evidence without raw API bodies or credentials.

0.135.0 introduced the generic Shipment Framework `creation_attempt_id` contract before controlled PEK production submit. 0.135.1 hardened that contract after code review: create mutation locks now match the canonical order plus carrier repository slot, lock release and stale takeover are token-owned, attempt metadata updates are serialized to avoid preview split/lost-update races, manual reconciliation moves pending attempts back to active, and terminal lifecycle transitions live in application/carrier services rather than storage. 0.135.2 kept the DB-level token-owned CAS and fixed stale positive option cache after direct SQL lock deletion, but mirrored `delete_option()` negative-cache semantics. 0.135.3 keeps CAS and changes lock cache cleanup to conservative unknown/re-read-DB semantics. 0.135.4 added safe PEK diagnostics for preregistration, sender warehouse, pickup destination, SMS, and checkout pickup access failures. 0.135.5 used that evidence to fix the exact preregistration services contract: PEK required explicit `hardPacking`, `strapping`, `documentsReturning`, and `delivery` service objects, so unordered optional services now send `enabled=false`, pickup sends `delivery.enabled=false`, and courier sends `delivery.enabled=true` with payer type 1. `hardPacking=false` is intentionally unrelated to the shop light-cargo bag surcharge, insurance and sealing behavior are unchanged, and no `storing` or undocumented bag fields are added. 0.135.5 produced the first successful production PEK submit: the shipment exists in the PEK cabinet and document/label downloads work. 0.135.6 handles the follow-up live status sentinel `cargoStatusId=-1` by treating it as "status ID not assigned yet", preserving the valid `cargoStatus` string and other status fields while omitting `pek_cargo_status_id`; other negative IDs remain invalid and adapter status updates return controlled errors instead of WooCommerce Critical. 0.135.7 extends that bounded live compatibility to the exact string sentinel `cargoStatusId="-1"` and makes PEK cancellation mutation one-shot with fresh read-only status reconciliation. 0.135.8 handles the exact cancelled live wire shape: `cargoStatus="Аннулировано до приемки груза"` with integer `cargoStatusId=-3`. The `-3` value is accepted only with that cancelled-before-acceptance status text, is not persisted, and clears stale positive status IDs. String `"-3"` and all other negative IDs remain contract errors. 0.135.9 uses that fresh `CANCELLED` status as terminal lifecycle evidence: status update terminalizes the existing attempt and removes active PEK shipment storage automatically, without calling `/order/cancellation/` or adding a broad terminal archive policy. PEK still derives `customerCorrelation` from the generic attempt identity; no PEK builder or resolver generates random lifecycle IDs.

0.135.10 adds the exact courier PEK preregistration follow-up: the first controlled courier create reached `/preregistration/submit/` after sender warehouse, courier destination, counterpart, SMS, CODMaxSum, and declared-value checks all passed, but PEK returned HTTP 200 logical validation for missing `cargos[0].services.sealing`. The live order had product weight 8800 g and `sealing=false`, so the request builder now always serializes the `sealing` service object: light cargo keeps `enabled=true` with sender payer, and non-sealed cargo sends `enabled=false` with no payer. This extends the 0.135.5 required service-object evidence for `hardPacking`, `strapping`, `documentsReturning`, and `delivery`; it does not add `storing`, bag aliases, hardPacking conflation, plannedDate, receiver, SMS, insurance, correlation, checkout, or courier geography changes. 0.135.10 also hardens the 0.135.9 CANCELLED lifecycle DI: `PekShipmentStatusService` requires `ShipmentCreationAttemptService` and terminalizes the attempt before repository deletion without a nullable silent fallback.

0.135.11 keeps the successful 0.135.10 courier preregistration payload unchanged and adds bounded PEK status DateTime compatibility for exact live evidence. The first status update for that newly created courier cargo failed only while normalizing `cargos[].info.deliveryPlanDate`; diagnostic phase captured production value `2026-08-19T22:23:16.833`. Official PEK `/cargos/status/` documentation shows `deliveryPlanDate` as a `DateTime` with example `2021-08-19T00:00:00`, so production emits a more precise 3-digit millisecond representation than the example. 0.135.11 accepts `Y-m-d\TH:i:s.v` only for `deliveryPlanDate`, preserves the original string unchanged, does not invent a timezone, and keeps malformed status dates on the PEK status normalization exception with safe `field`, `value_type`, and bounded scalar `value` logger context. No parsing is broadened through `strtotime()` or generic `DateTimeImmutable`.

0.137.0 adds and live-verifies the PEK international calculation runtime for the fixed sender-country scope `RU -> RU/AM/BY/KG/KZ`. Checkout live verification covered KZ/Almaty, BY/Minsk, AM/Yerevan, and KG/Bishkek pickup, courier, pickup map, selected-terminal repricing, correct PEK tariffs, and order creation; order-admin recalculation/save and foreign manual cargo-code attach/status/actual-cost tracking were also verified. Checkout and order recalculation keep the existing `pek:pickup` and `pek:courier` rates, PEK pickup provider, own/partner pickup presentation, selected-terminal repricing, RUB calculator currency contract, and country-aware location/provider fingerprints. PEK automatic shipment creation remains intentionally RU-only. Foreign PEK orders are created manually in the PEK cabinet, then attached by cargo code for automatic status and actual-cost tracking where `/cargos/status/` supports the code. International preregistration, cancellation mutations, document-download workflow for manually attached foreign cargo, accepted-cargo return, recipient identity/tax/customs workflows, and the PEK paid "Сопроводительные документы" service are not implemented in this release.

0.136.0 added an administrator-facing PEK status mapping tab under Delivery services -> PEK -> Статусы ПЭК. The catalog is code-owned, stored through `SettingsRepository`, and has independent universal-status selects for pickup and courier, including the delivery-type-specific `Прибыл` default and the fixed `Выдан мест N из M` pattern row. Editable mapping affects WDC/order business status only; PEK cancellation recognition, pre-acceptance safety, accepted-cargo protection, and automatic cancelled cleanup continue to use immutable raw carrier predicates.

## Current Carrier Scope

CDEK uses one carrier key and one delivery service key, both `cdek`. The existing CDEK service can be enabled per country for `RU`, `AM`, `BY`, `KZ`, and `KG` through the delivery-service country repository; there is no separate international CDEK carrier or service.

Jet Logistic uses one carrier key, `jet_logistic`, and one delivery service key, `jet_logistic`. Its runtime carrier returns two stable rates from one API calculation: `jet_logistic_pickup` and `jet_logistic_courier`. Jet pickup is a pickup delivery type but does not require a concrete pickup point, because the Jet API returns terminal cities rather than warehouse identifiers.

PEK uses one stable carrier key and one delivery service key, both `pek`. Version 0.136.0 keeps the verified PEK Shipment Framework implementation for RU LTL `type=3`, `orderType=0`: sender self-delivery to a PEK warehouse, shipment-modal sender warehouse override, pickup and courier recipient modes, physical recipient with SMS release, mandatory insurance, sender-paid services, framework-owned creation attempts, persistence mapper, manual attach by cargo code, status/autosync, actual cost from `/cargos/status/` `services.sum`, application/label PDFs through the document provider, pre-acceptance cancellation through `/order/cancellation/`, and local removal after acceptance. The first successful production submit and document downloads are confirmed. Cancellation remains one-shot and uses read-only fresh status reconciliation on ambiguous outcomes; status update that freshly proves PEK cancelled-before-acceptance converges to the same terminalize/delete local lifecycle without a carrier mutation, independent of editable universal-status mapping. Accepted-cargo return, accounting documents, CargoInvoice/CargoAssignment flows, and `/cargos/cancelandreturncargo/` remain out of scope. Courier `addressStock` is built only from persisted order destination data: shipping DaData/Woo fields remain authoritative when shipping is filled, billing DaData can only fill an empty or semantically identical destination, stale DaData is rejected against current Woo fields, country must be current RU, typed apartment/office/premise/corpus/structure units, including full DaData type values, are preserved through checkout order meta and raw Woo address fallback, selected-location/city/settlement FIAS identifiers are carried for every courier address source, including Woo fallback, and fail closed on explicit mismatch without confusing house/full-address FIAS with locality FIAS. After that canonical identity guard succeeds, courier shipment geography uses `/branches/findzonebyaddress/` with the actual full recipient address as final branch authority, exposes only precision/zone/main-warehouse/formatted-address hashes, and never uses canonical city-centroid coordinates for the shipment branch. Counterpart confirmation is bound to sender identity and PEK account login hash; the official confirmed counterpart list may contain `legalForm=1/2/3`, but PEK sender matching in this plugin supports only legal entity/IP rows (`1/2`) and skips physical-person rows (`3`) before reading optional fields, so physical documents, FIO, GUID, card, INN/KPP, and raw rows are never persisted, logged, or rendered. Settings save validates before writing, PEK sender and recipient phones share one fail-closed RU normalizer instead of cleaning malformed text into a valid number, SMS availability uses exact declared-value cache keys plus strict official list/scalar boundaries, and status updates use a required typed normalizer with strict DateTime, exact cargo cardinality, presence-aware optional fields, bounded live sentinel handling for `-1`/`"-1"`/cancelled-status integer `-3`, safe bounded diagnostics for unsupported status DateTime fields, configurable universal status mapping, and fail-closed actual-cost parsing. Pending uncertain PEK submissions still surface manual reconciliation in the shared UI: managers can attach the cargo code or remove the local pending record after checking the PEK cabinet, while duplicate automatic create stays blocked.

Ozon Delivery version 0.139.6 stores only the active full pickup snapshot: obsolete point rows are cleaned after a confirmed activation commit. Migration `0054` replaces raw `schedule_json` with presentation-ready `schedule`; no legacy backfill is performed. Before the first live import after this migration, clear both Ozon pickup tables manually if they have not already been cleared.

Version 0.133.9 connected the carrier-agnostic pickup-point provider contract and PEK geography/destination pickup foundation to checkout runtime while Shipment Framework integration was still absent. In the current 0.136.0 line PEK Shipment Framework integration exists, the first controlled production submit succeeded, cancellation follow-up is handled through read-only reconciliation, cancelled-status integer `-3` compatibility is bounded to the exact cancelled-before-acceptance status, fresh PEK cancelled status update removes the active PEK shipment automatically, and PEK universal status mapping is administrator-configurable without changing carrier safety; automated work must still use fake/local PEK HTTP. PEK still resolves canonical `wp_wdc_locations` into carrier-owned mappings, keeps PEK zone/branch/main-warehouse data outside canonical locations, and never uses PEK `warehousePoint` as destination coordinates. Destination terminal discovery keeps the documented `/branches/nearestdepartments/` contract with non-empty address plus optional decimal-string coordinates. In checkout, public pickup REST first bootstraps the existing WooCommerce customer session for the current request, then uses the PEK provider only through server-owned `pickup_provider_query` metadata saved inside the production `rate_meta` envelope of the selected rate; browser cargo/location/coordinates/radius/limit/address are not trusted. Session bootstrap failure is reported as `provider_session_unavailable` (503), while a successfully loaded session without a valid stored rate still reports `provider_rate_context_missing` (400). The top-level session rate envelope owns carrier, service, delivery type, pickup family, and requirement flags, while nested `rate_meta` owns carrier-specific provider context. Trusted snapshots allow either a bounded numeric coordinate pair or address-only `null/null` coordinates; partial, empty-string, non-numeric, and out-of-range coordinates fail closed. Full destination address is not stored in the session snapshot: `location_id` remains the authority and the PEK provider reloads the canonical mapping/address server-side. Saving a PEK terminal accepts only a point code, fresh-validates it through `resolve_selection()`, preserves the PEK provider SHA-256 as `provider_destination_fingerprint`, keeps the generic checkout location fingerprint separate, and triggers a rate refresh. The selected warehouse ID becomes calculator `receiverWarehouseId`; a provider-valid point can still fail calculator pricing, so selected-terminal quote failure is recoverable: PEK marks the current recovered rate with generic rejected-selection metadata, checkout clears only `pek:pickup`, restores an explicit preliminary PEK rate, keeps the PEK method selected when recovery succeeds, and renders an inline transient message inside that shipping method. The server event is removed before session/order/calculation persistence; the checkout page keeps the message only in module memory across internal stabilization recalculations. DOM hidden fields, local `selectedPickupPoints`, and POST save 200 are not treated as calculator success; only post-calculation `/checkout/state` with a valid family selection clears the message. Authoritative empty state removes stale local selections but leaves the recovery message visible. Destination change, method change, and browser reload still clear it. Free PEK points render as `Собственный пункт выдачи ПЭК`; paid points render as `Партнерский пункт выдачи ПЭК` with a possible surcharge warning. Internal warehouse UUIDs remain technical `point_code` metadata and are not used as customer-facing titles.

Version 0.133.9 uses the PEK quote/calculator foundation in buyer checkout. `PekApiClient::calculate_price()` remains the typed POST boundary for `/calculator/calculateprice/`; `PekCarrier` reuses `PekQuoteService` to produce pickup and courier `DeliveryRate` objects without rebuilding payloads. The calculator payload always sends `isHP=false` and `sealingPositionsCount=0`; store-owned configurable bag/plombing surcharges are kept separate from PEK services and added to final pre-rules `price_kopecks`. For saved checkout/order calculation data, PEK `api_base_price_rub` is the adjusted base before rules (`costTotal` plus store surcharges), while `pek_carrier_base_price_rub` and `pek_carrier_price_kopecks` preserve the pure PEK `costTotal`. The response parser still treats PEK `costTotal` as authoritative carrier cost, keeps safe service breakdown only, preserves endpoint/status metadata, and redacts carrier messages/field errors through the quote service boundary. Rule formula visualization shows `Добавлен мешок и пломбировка`, `Добавлен мешок`, or `Добавлена пломбировка` when the corresponding configured store surcharge is non-zero; these lines are not Rule Engine entries and do not affect `price_delta_rub`. Checkout quote cache distinguishes preliminary and selected terminals by point code plus provider destination fingerprint, and also includes courier address scope, full-address fingerprint, planned datetime bucket, sender warehouse, surcharge settings, product weight, transport fields, and generic destination/pickup-selection fingerprints without raw credentials or contract identifiers. PEK plannedDateTime is memoized per resolver instance so one request lifecycle uses the same value for quote cache context and calculator payload.

PEK schema integrity is checked in the controlled migration lifecycle, not during diagnostics or repository lookups. Migration history is not treated as proof that physical tables still exist: `0050_repair_pek_foundation_schema.php` delegates to the carrier-owned `PekSchemaIntegrityService`, checks both PEK foundation tables with the active WordPress prefix, creates only missing tables through the existing repository installers, verifies postconditions, and fails the migration if either table is still absent. The location mapping physical column is `mapping_precision` because `precision` is reserved in MySQL 8; the domain mapping array still exposes `precision`, and the repository translates between domain and database rows. `0051_migrate_pek_mapping_precision_column.php` supports legacy tables by adding `mapping_precision` and backfilling from quoted legacy `` `precision` `` without dropping the old column. Installers check unavailable `dbDelta()` and `$wpdb->last_error`, and migration failures are logged/shown as safe admin notices instead of uncaught site-wide fatals. The recovery never drops, truncates, imports data, edits canonical locations, or calls PEK APIs.
