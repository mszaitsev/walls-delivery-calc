## Implemented Ozon Delivery foundation

Version 0.147.3 keeps the buyer-facing Ozon Delivery runtime for `Ozon до ПВЗ` and the independent `Ozon курьером` checkout rate, and adds Ozon courier shipment creation through the existing Shipment Framework lifecycle. Pickup continues to use the local pickup catalog, selected-point repricing, and shipment `delivery.delivery_point.delivery_point_id`; courier checkout uses official `/v1/order/checkout` `delivery.courier.coordinates.latitude/longitude` from server-confirmed DaData exact-address coordinates or the 1 km Ozon pickup proxy for preliminary pricing. Courier shipment create never uses that proxy as address authority. Order creation may freeze generic `_wdc_platform_structured_recipient_address` from trusted checkout DaData evidence; legacy/missing snapshots use the Woo recipient address only as input for server-side Shipment modal normalization. Ozon shipment modal normalization carries `selected_location_id` and `selected_location_fias_id` from server-owned order snapshot/meta/calculation context, ignores browser modal location/FIAS fields, and fails closed when server-owned selected location FIAS conflicts with DaData `city_fias_id`/`settlement_fias_id`. The Ozon courier modal keeps Create disabled until the existing server-side normalized address result confirms street, house/stead, required structured fields, and valid coordinates; manager edits clear the stale result until the address is analyzed again. `/v1/order/create` courier payload uses official `delivery.courier` fields: required `coordinates.latitude`, `coordinates.longitude`, `zip_code`, `country`, `region`, `city`, `street`, plus optional `house_number`, `entrance`, `floor`, `apartment`, and `intercom`. Shipment-time preflight `/v1/order/checkout` is derived from the same canonical create body, preserving postings, shipment method, dimensions, declared values, recipient phone, and courier coordinates while stripping create-only delivery address fields. Browser coordinates/FIAS are not authority. Existing pickup create payload, actual-cost preflight, declared-value model, external IDs, cancellation polling, return reconciliation, status mapping settings, label filenames, creation confirmation, manual attach, order-admin selected-rate pickup context, Shipment modal point-limit validation, and local remove text remain unchanged.

Delivery service country storage keeps `wp_wdc_delivery_service_countries` with the unique `service_country (service_id, country_code)` contract. Version 0.145.1 makes `replace_countries()` an exact but diff-based replace: normalized equal sets perform no writes, stale rows are deleted selectively, and missing rows use duplicate-safe UPSERT without changing existing `created_at`. This preserves bootstrap self-healing for builtin `RU` services while removing the previous DELETE-all/INSERT-all race on ordinary WordPress requests.

# ТЗ v0.2: плагин расчета, выбора и оформления доставок для WooCommerce

> Примечание: этот документ описывает целевое состояние продукта и полный объем требований. Фактический статус реализации, текущая готовность блоков, технические остатки и ближайший roadmap ведутся отдельно в `docs/project-status.md`.

## 1. Общая цель плагина

Разрабатываем полноценный модуль доставки для WordPress/WooCommerce, работающий на классическом WooCommerce checkout через стандартный механизм shipping rates. Плагин должен:

1. рассчитывать доступные варианты доставки по стране/городу/весу/стоимости заказа/ТК/типу доставки;
2. показывать покупателю варианты доставки стандартным списком WooCommerce;
3. показывать цену, срок, примерную календарную дату доставки и, если применимо, перечеркнутую цену “до скидки”;
4. позволять выбрать ПВЗ только после выбора метода “до ПВЗ”;
5. делать поле адреса обязательным только при выборе курьерской доставки;
6. сохранять выбранную доставку в заказе;
7. позволять менеджеру пересчитать доставку в уже созданном заказе;
8. создавать отправления в ТК;
9. получать статусы, документы и номера отправлений;
10. автоматически менять WooCommerce-статус заказа по статусу доставки;
11. работать с несколькими ТК и с несколькими псевдо-ТК фиксированной/ручной стоимости.

Технически расчет ставок делаем через WooCommerce Shipping API: метод доставки рассчитывает ставки в `calculate_shipping()` и добавляет варианты через `add_rate()`. Это соответствует стандартному механизму WooCommerce для cart/checkout. ([The WooCommerce Developer Blog][1])

Плагин сразу проектируем с учетом HPOS: данные заказа читаем и пишем через WooCommerce CRUD/API, без прямой зависимости от `wp_posts/wp_postmeta` для заказов. WooCommerce прямо указывает, что при HPOS структура хранения заказов меняется, а расширениям нужно использовать WooCommerce-specific APIs. ([The WooCommerce Developer Blog][2])

Для фоновых задач используем Action Scheduler: синхронизация статусов, очистка кешей, ротация логов, проверка изменений ГАР/ФИАС, удаление старых документов. Action Scheduler предназначен для фоновых задач в WordPress-плагинах, поддерживает отложенные/повторяющиеся хуки, логи и масштабируемую очередь. ([Action Scheduler][3])

# 2. Checkout: поведение для покупателя

## 2.1. Ввод страны, города и адреса

На checkout покупатель выбирает страну и город/населенный пункт. Адрес может быть введен сразу, но до выбора курьерской доставки он не обязателен.

Поле города WooCommerce используется как точка входа в наш поиск населенного пункта. При вводе от 3 символов открывается поиск по локальной базе населенных пунктов ФИАС/ГАР:

* результат группируется по регионам;
* формат строки: `Населенный пункт — Область`;
* на desktop — 2 колонки, на mobile — 1 колонка;
* точные совпадения поднимаются выше;
* хорошие совпадения по региону поднимают регион выше;
* при выборе города из справочника заполняем:

  * город;
  * регион;
  * базовый почтовый индекс города;
  * внутренний `fias/gar id`, если он есть;
* если покупатель потом вводит нормализованный адрес, базовый индекс заменяется на уточненный индекс по адресу.

Если совпадений нет, показываем кнопку “Выбрать этот населенный пункт”. При таком fallback:

* используем введенное покупателем значение города;
* регион и индекс не заполняем;
* такой fallback-город не сохраняем в справочник и не выносим на ручную обработку.

## 2.2. Расчет вариантов доставки

После выбора города плагин рассчитывает доступные варианты доставки. Один вариант на фронте:

```text
ТК + тип доставки + срок + итоговая цена
```

Пример:

```text
СДЭК — доставка до ПВЗ, 4 дня: 430 ₽
```

Если применена скидка на доставку:

```text
Почта России — доставка до ПВЗ, 9 дней: 1 ₽, зачеркнуто 450 ₽
```

На фронте дополнительно показываем примерный календарный срок:

```text
Доставка планируется примерно на 26 мая, вторник.
```

Если ТК возвращает диапазон сроков или мы получаем диапазон после правил, выводим диапазон:

```text
Доставка планируется примерно 26–28 мая.
```

## 2.3. Доставка до ПВЗ

Если покупатель выбрал метод доставки до ПВЗ, только тогда появляется блок выбора ПВЗ для конкретной ТК/метода.

По кнопке “Выбрать пункт выдачи” открывается модальное окно с картой и списком ПВЗ. Покупатель выбирает ПВЗ, после чего в заказ сохраняются только:

* код ПВЗ;
* адрес ПВЗ.

Прочую информацию по ПВЗ в заказе не сохраняем, если она не понадобится конкретной ТК при создании отправления.

Если выбранный ПВЗ меняет стоимость доставки, пересчитываем rate. Комментарий “доплата за выбранный пункт выдачи” показываем только если итоговая цена для покупателя реально изменилась. Если из-за акции доставка была 1 ₽ и после пересчета осталась 1 ₽, комментарий об изменении цены не показываем.

## 2.4. Курьерская доставка

Если покупатель выбрал курьерскую доставку, стандартное поле адреса WooCommerce становится обязательным.

Адрес нормализуем через ФИАС/ГАР. Если ФИАС недоступен, превышены лимиты или адрес не найден, используем fallback: сохраняем введенный покупателем адрес без нормализации.

Также закладываем fallback на DaData, но как отдельную настраиваемую опцию, потому что у него есть лимиты и он не должен быть обязательной зависимостью.

## 2.5. Сортировка вариантов доставки

На checkout добавляем покупателю сортировку:

```text
По цене доставки: от минимальной к максимальной
По сроку доставки: от минимального к максимальному
```

Если внутри одного метода ТК есть несколько тарифов, сортировка по сроку учитывает все тарифы внутри этого метода. Для верхнего уровня метода используем минимальный итоговый срок среди доступных тарифов, а внутри раскрытого списка тарифов также сортируем тарифы по выбранному критерию.

## 2.6. Запоминание выбора

Выбранные город, доставка, тариф и ПВЗ сохраняются:

* в WooCommerce session;
* дополнительно в browser storage с TTL.

Это нужно, чтобы при возврате на checkout выбор не сбрасывался полностью.

# 3. Расчет календарной даты доставки

## 3.1. Базовый алгоритм

Плагин должен показывать покупателю не только количество дней, но и примерную дату доставки.

Алгоритм:

1. Берем дату создания заказа или текущую дату расчета на checkout.
2. Определяем дату сдачи посылки в ТК:

   * день заказа не считается днем обработки;
   * магазин обрабатывает заказ заданное количество рабочих дней;
   * срок обработки магазина настраивается в админке;
   * по умолчанию — 1 рабочий день.
3. Срок доставки ТК считается не включая день сдачи посылки в ТК.
4. Если срок доставки ТК после правил равен `N` календарных дней, итоговая дата доставки = дата сдачи в ТК + `N` календарных дней.
5. Если срок доставки ТК указан в рабочих днях, adapter/rule engine переводит его в календарную дату с учетом календаря выходных/праздников.

Пример 1:

```text
Заказ: 20 мая, среда.
Обработка магазина: 1 рабочий день.
Сдача в ТК: 21 мая, четверг.
Срок ТК: 5 календарных дней, день сдачи не считается.
Плановая доставка: 26 мая, вторник.
```

Пример 2 по вашей логике:

```text
Заказ: 23 мая, суббота.
Обработка магазина: 1 рабочий день.
Воскресенье — выходной.
Сдача в ТК: 25 мая, понедельник.
Срок ТК: 5 календарных дней.
Плановая доставка: 30 мая.
```

Важное замечание: если речь о 2026 годе, то **30 мая 2026 — суббота, а не пятница**. В плагине день недели будет вычисляться по реальному календарю, чтобы такие расхождения не попадали на фронт.

## 3.2. Календарь рабочих и выходных дней

В админке нужен визуальный календарь по годам.

Функции:

* при разработке сразу создаем календарь 2026 года;
* админ может сформировать следующий год вручную;
* если следующий год не сформирован, 1 декабря он создается автоматически;
* после автосоздания следующего года вешаем badge в меню WDC и уведомление в настройках;
* после первого ручного сохранения календаря badge и уведомление снимаются;
* админ может кликнуть любой день и изменить его статус;
* данные сохраняются по годам.

Чтобы снять противоречие между “суббота считается рабочей для магазина” и “суббота/воскресенье на старте календаря помечаются выходными”, предлагаю сделать два слоя:

1. **Общий календарь выходных/праздников РФ**
   На старте субботы и воскресенья помечаются как выходные. Используется для перевода сроков ТК из рабочих дней в календарные.

2. **Календарь обработки магазина**
   Наследует общий календарь, но суббота для обработки магазина считается рабочей, если она не отмечена админом как специальный выходной магазина.

Это нужно подтвердить, потому что иначе правила для субботы конфликтуют.

# 4. Данные, сохраняемые в заказе WooCommerce

При создании заказа сохраняем компактный, но достаточный snapshot доставки.

## 4.1. Сохраняемые данные

В order meta / shipping item meta сохраняем:

* ТК;
* тип доставки: ПВЗ или курьер;
* выбранный тариф;
* исходная стоимость от ТК;
* итоговая стоимость для покупателя;
* цена “до скидки”, если есть промо-скидка;
* исходный срок от ТК;
* срок после правил;
* плановая календарная дата доставки;
* примененная формула/список правил;
* выбранный ПВЗ: код и адрес;
* адрес курьерской доставки;
* нормализованный адрес, если нормализация успешна;
* package snapshot:

  * вес;
  * габариты;
  * объем;
  * объявленная стоимость;
* тип состава грузомест:

  * подробный состав по заказу WooCommerce;
  * либо объединенная строка `Товары по заказу {{номер заказа WooCommerce}}`.

Raw carrier quote/reference не сохраняем по умолчанию, чтобы не раздувать БД. Возможность сохранять raw API response включаем только в debug-режиме и с ротацией логов.

## 4.2. Примечания к заказу

При изменении способа доставки менеджером в админке добавляем системное примечание:

```text
Доставка “старое название метода” по цене X ₽ заменена на “новое название метода” по цене Y ₽.
```

Используем только название и цену метода доставки, без дополнительных технических полей.

# 5. Транспортные компании

## 5.1. Приоритет первого полного API-цикла

Приоритет интеграций:

1. Почта России;
2. СДЭК;
3. DPD;
4. Yandex.Доставка “доставка в другой день”.

Перед интеграцией каждого API делаем ручную проверку актуальности базовых методов через ваши PowerShell-запросы на локальном компьютере.

## 5.2. Yandex.Доставка

Yandex.Доставку включаем в разработку как полноценную ТК для доставки по России по модели “доставка в другой день”.

Документация Яндекса описывает API доставки по России как возможность оформить заказ в другой день через HTTP-запросы, включая классический забор со склада, самопривоз в точки отгрузки и доставку до ПВЗ. ([Yandex][4])

В списке методов есть:

* предварительный расчет стоимости через `pricing-calculator`;
* получение расписания вывозов;
* определение `geo_id`;
* получение списка ПВЗ;
* создание офферов;
* подтверждение оффера;
* получение информации и статуса заявки;
* история статусов;
* отмена заявки;
* создание заказа;
* редактирование грузомест;
* генерация ярлыков и актов. ([Yandex][5])

Для расчета Яндекс поддерживает тарифы `time_interval` — доставка до двери, и `self_pickup` — доставка до ПВЗ. В запросе расчета передаются суммарный вес, оценочная стоимость и грузоместа с весом/габаритами. ([Yandex][6])

Для ПВЗ Яндекс предоставляет метод получения точек самопривоза/ПВЗ/постаматов; можно фильтровать по `geo_id`, типу точки, операторам и способам оплаты. ([Yandex][7])

При создании заявки Яндекс принимает `items`, `places`, данные получателя, способ последней мили `time_interval` или `self_pickup`, а также возвращает интервалы доставки/забора и стоимость. Это хорошо ложится на нашу модель товаров и нескольких грузомест. ([Yandex][8])

## 5.3. Фиксированные и ручные службы доставки

“Фиксированная стоимость” должна быть не одной встроенной службой, а типом псевдо-ТК, которые админ может добавлять в любом количестве.

Для каждой такой службы задается:

* название;
* страны/города/регионы действия;
* тип доставки: ПВЗ, курьер, иной текстовый вариант;
* срок;
* стоимость;
* комментарий;
* условия доступности;
* возможность пропустить через общий rule engine.

В ручных тарифах нужно поддержать два типа таблиц:

1. **Цена за 1 кг**
   Например: город/направление → `1 кг = X ₽`.

2. **Диапазоны веса**
   Таблица вида:

```text
от 0 до 2 кг = X ₽
от 2 до 5 кг = Y ₽
от 5 до 10 кг = Z ₽
```

# 6. Rule Engine: правила стоимости и срока

## 6.1. Назначение

Rule engine применяет бизнес-правила к исходной стоимости/сроку от ТК или ручной таблицы.

Правила могут:

* изменить стоимость доставки;
* изменить срок доставки;
* добавить комментарий;
* отключить службу/тариф;
* применить промо-скидку на доставку.

## 6.2. Структура правила

Каждое правило:

* название;
* что изменить:

  * стоимость;
  * срок;
  * комментарий;
  * доступность службы;
* как изменить:

  * увеличить на;
  * уменьшить на;
  * равно;
* величина изменения до 4 знаков после запятой;
* база:

  * рубли;
  * % от стоимости доставки;
  * % от стоимости заказа;
  * % от стоимости заказа + доставки;
* условия:

  * 1–3 условия;
  * комбинация через И/ИЛИ;
* флаг “Скидка на доставку по акции”.

Промо-правило всегда применяется последним. Перед ним запоминается цена “до скидки”. После всех правил применяется минимальная стоимость доставки.

## 6.3. Audit trail

Для каждого расчета сохраняем техническую цепочку:

```text
исходная цена ТК
правило 1 → результат
правило 2 → результат
промо-правило → цена до скидки / цена после скидки
минимальная стоимость → итог
```

В заказе менеджер видит формулу расчета. На checkout покупатель видит только итоговую цену, срок и перечеркнутую цену, если применимо.

# 7. Кеширование расчетов

## 7.1. Ключ кеша

Кеш итогового расчета должен учитывать минимум:

* страну;
* город / FIAS-GAR ID, если есть;
* вес;
* стоимость заказа;
* ТК;
* тип доставки;
* календарную дату расчета.

Также технически нужно добавить `package_fingerprint` по габаритам/объему, если конкретная ТК использует габариты в расчете. Иначе одинаковый вес и стоимость, но разные размеры могут ошибочно получить один кешированный тариф.

Параметры правил в ключ кеша не включаем. Вместо этого:

* при любом изменении правил кеш расчетов сбрасывается;
* в админке есть кнопка ручного сброса кеша стоимости доставок.

## 7.2. TTL

TTL расчетного кеша короткий:

* максимум до конца текущего календарного дня;
* на следующий день расчет всегда выполняется заново;
* если API ТК недоступен, но есть последний валидный кеш за текущий день, используем его;
* если кеша нет и API не ответил — ТК просто не возвращает варианты.

## 7.3. Таймауты API

При расчете доставки через API обязательно задаем жесткие таймауты.

Принцип:

* каждый запрос к ТК имеет короткий timeout;
* каждая ТК имеет собственную настройку timeout, с безопасным дефолтом;
* общий расчет checkout не должен подвешиваться из-за одной ТК;
* если ТК не ответила, ее варианты не показываются;
* ошибка пишется в лог, покупателю не показывается;
* если ни одна ТК не дала расчет, показываем единый fallback-метод.

Fallback-метод:

```text
Нет видимых доступных вариантов доставки, обратитесь к менеджеру магазина
Стоимость: 0 ₽
```

Это технический бесплатный метод, чтобы checkout не ломался, но он не должен создавать автоматическую отправку в ТК.

# 8. ПВЗ и карта

## 8.1. Получение ПВЗ

Список ПВЗ окончательно реализуем после разработки каждого carrier adapter.

Базовая стратегия:

* ПВЗ грузим по текущему запрошенному городу, а не по всей России;
* запрос инициируется в момент выбора метода доставки до ПВЗ или открытия выбора ПВЗ;
* кешируем до конца текущего дня;
* ключ кеша ПВЗ:

  * страна;
  * регион;
  * город;
  * ТК;
  * дата;
* список ПВЗ не сохраняем в заказе полностью.

## 8.2. Карта

Основной вариант — Яндекс Карты + Яндекс Геокодер:

* ключ карты Яндекса хранится в общих настройках;
* ключ геокодера Яндекса хранится отдельно;
* геокодер используется для поиска адреса на карте и встроенной поисковой строки;
* ПВЗ показываются маркерами;
* при клике на маркер показываем адрес, режим работы, комментарий, если есть;
* кнопка “Забрать здесь”.

Альтернативный вариант карты можно заложить архитектурно, например Leaflet/OpenStreetMap, но использовать его как полноценный fallback стоит только после отдельной проверки условий использования геокодинга и лимитов. Для России основной рабочий вариант — Яндекс.

# 9. ФИАС/ГАР, города и нормализация адресов

## 9.1. Локальная база населенных пунктов

Разово локально формируем компактную базу из официальных данных ФИАС/ГАР:

* регионы;
* населенные пункты;
* типы населенных пунктов;
* базовые индексы;
* FIAS/GAR identifiers;
* связи регион → населенный пункт.

В WordPress загружаем не полную адресную базу, а компактный справочник, достаточный для выбора города и региона.

## 9.2. Нормализация адреса

Нормализация адреса:

* используется на checkout;
* используется в админке заказа;
* используется в профиле покупателя;
* включается/выключается отдельной настройкой плагина.

Если сервис не отвечает, лимиты превышены или адрес не найден:

* не блокируем checkout;
* не блокируем менеджера;
* сохраняем введенный адрес как fallback;
* в технических данных помечаем адрес как ненормализованный.

## 9.3. Изменения ФИАС/ГАР

Нужно протестировать и, если API работает стабильно, реализовать периодическую обработку изменений через сервис “Получение сведений из ГАР”, раздел Changes.

В Swagger сервиса видны методы Changes, включая `GET /api/spas/v2.0/GetChanges` для постановки задачи на получение списка измененных адресных объектов за интервал, `GetSearchTaskStatus` для состояния задачи и `GetSearchResultBlock` для получения блоков результата. ([fias-public-service.nalog.ru][9])

План работы:

1. Раз в неделю Action Scheduler запускает проверку изменений.
2. Плагин получает изменения по объектам, релевантным нашей базе населенных пунктов/регионов.
3. Изменения сохраняются как pending.
4. В меню WordPress появляется badge.
5. В настройках WDC админ видит список изменений.
6. Плагин предлагает автоматический мэтчинг с базами городов ТК.
7. Конфликтные случаи уходят на ручную обработку.
8. После подтверждения админом badge снимается.

Fallback-города, введенные покупателями вручную, в эту систему не добавляем.

# 10. Статусы доставки и WooCommerce statuses

Новые WooCommerce-статусы плагин не создает. Вы создаете их отдельно существующим плагином, а WDC только использует уже готовые WooCommerce statuses для сопоставления.

В WDC задаются:

1. внутренние стандартизированные статусы доставки;
2. маппинг статусов каждой ТК → внутренний статус WDC;
3. маппинг внутренний статус WDC → существующий WooCommerce status;
4. список WooCommerce statuses, в которых заказы участвуют в автоматическом опросе;
5. WooCommerce statuses, в которых заказ не опрашивается;
6. terminal statuses доставки;
7. интервал опроса;
8. добавлять ли системное примечание к заказу при смене статуса.

Не опрашиваем:

* терминальные отправления;
* отправления, уже получившие статус “доставлен/завершен”;
* заказы WooCommerce в завершенном статусе, причем конкретный WooCommerce status настраивается;
* заказы в WooCommerce statuses, исключенных из обработки.

Дубликат “Отменен/Отменён” в исходном списке статусов приводим к одному внутреннему canonical status `cancelled`, с отображаемым названием “Отменён”.

# 11. Отправка заказа в ТК

## 11.1. Общая форма отправки

В заказе WooCommerce менеджер открывает форму отправки в ТК.

Общая часть формы:

* ТК;
* тип доставки: ПВЗ/курьер;
* тариф;
* возможность выбрать другой тариф;
* терминал/ПВЗ отправления, настроенный для конкретной ТК;
* редкий вариант курьерского забора от магазина, если он поддерживается ТК, например СДЭК;
* данные получателя:

  * ФИО;
  * телефон;
  * email;
  * страна;
  * регион;
  * город;
* ПВЗ получения или адрес курьера;
* вес посылки;
* грузоместа;
* габариты грузомест;
* товары;
* объявленная стоимость;
* страховка;
* дополнительные услуги.

Наложенный платеж/COD не закладываем.

Страховая/объявленная стоимость = стоимость товаров за вычетом скидок:

* акционная цена товара;
* купоны/промокоды;
* скидки через fee на checkout.

Доставка в страховую стоимость не входит.

## 11.2. Вес и габариты при создании отправления

При регистрации отправления менеджер всегда вводит фактические данные вручную.

Вес:

* плейсхолдер = сумма веса товаров + вес упаковки по таблице;
* поле обязательно;
* ноль запрещен;
* дробную часть можно вводить точкой или запятой;
* значение нормализуется к единому числовому формату.

Габариты:

* три отдельных поля:

  * длина, см;
  * ширина, см;
  * высота, см;
* только целые значения в сантиметрах;
* ноль запрещен;
* удобный переход между полями через TAB;
* плейсхолдер не нужен.

## 11.3. Несколько грузомест

Сразу закладываем отправления с несколькими местами.

В adapter capability каждой ТК указываем:

```text
supports_multi_place
supports_itemized_places
supports_place_declared_value
supports_place_dimensions
supports_place_items
```

В форме отправки:

* менеджер может добавить несколько грузомест;
* для каждого грузоместа вводит вес и габариты;
* товары заказа распределяются по грузоместам;
* если товар имеет количество больше 1, количество можно разделить между местами;
* все количества должны быть распределены полностью;
* объявленная стоимость мест должна сходиться с объявленной стоимостью заказа;
* внутри каждого грузоместа можно включить “объединить товары”.

Если “объединить товары” включено внутри конкретного места, в ТК отправляется одна строка:

```text
Товары по заказу {{номер заказа WooCommerce}}
```

Если ТК не поддерживает несколько мест, UI не дает создать несколько мест для этой ТК или предупреждает, что нужно одно грузоместо.

## 15.2. Carrier Adapter Interface

Каждая ТК реализует единый интерфейс:

```php
interface CarrierAdapterInterface {
    public function get_key(): string;
    public function get_name(): string;
    public function get_capabilities(): CarrierCapabilities;

    public function quote(DeliveryQuoteRequest $request): DeliveryQuoteResult;
    public function get_pickup_points(PickupPointRequest $request): PickupPointResult;

    public function create_shipment(ShipmentCreateRequest $request): ShipmentCreateResult;
    public function get_shipment(ShipmentInfoRequest $request): ShipmentInfoResult;
    public function get_status(ShipmentStatusRequest $request): ShipmentStatusResult;
    public function get_documents(ShipmentDocumentsRequest $request): ShipmentDocumentsResult;

    public function health_check(CarrierHealthCheckRequest $request): CarrierHealthCheckResult;
}
```

Для ручных тарифов и фиксированных служб используется тот же интерфейс, но без API-части.

## 15.3. Работа с мелкими весами

У товаров всегда есть вес и габариты, но встречаются очень маленькие веса, например `0.003 кг`.

В adapter settings каждой ТК задаем:

* минимальный вес, который принимает API;
* единицы измерения API;
* способ округления:

  * вверх до грамма;
  * вверх до минимального порога ТК;
  * вверх до 10/50/100 г, если это потребуется конкретной ТК.

На этапе тестирования API каждой ТК проверяем минимально допустимые значения.

# 18. Что осталось подтвердить перед стартом

Остались четыре решения, которые лучше зафиксировать до первого Codex-этапа:

1. **Календарь:** подтверждаем ли двухслойную схему — общий календарь РФ с выходными субботами/воскресеньями и отдельную логику обработки магазина, где суббота считается рабочей?

2. **Кеш:** подтверждаем ли добавление `package_fingerprint` по габаритам/объему в ключ кеша, если конкретная ТК использует габариты в расчете? Это технически нужно, чтобы не получить неверный кеш для разных коробок с одинаковым весом.

3. **Fallback-метод:** подтверждаем ли, что fallback при полном отсутствии расчетов имеет цену `0 ₽` и название “Нет видимых доступных вариантов доставки, обратитесь к менеджеру магазина”?

4. **Часовой пояс расчета даты:** используем часовой пояс WordPress-сайта или отдельную настройку “часовой пояс склада”, по умолчанию Новосибирск? Для расчета “заказ сегодня” это важно, если заказ оформлен поздно вечером из другого часового пояса.
