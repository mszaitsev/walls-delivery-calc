0.137.0: PEK international calculation runtime is implemented and live-verified for `RU -> AM/BY/KG/KZ` plus existing `RU -> RU`. Version: 0.139.5

Ozon Delivery now has a local pickup-point catalog at `Службы доставки -> Ozon Доставка -> ПВЗ Ozon`. It is refreshed by a manual Action Scheduler job or, by default, once daily at the administrator-selected WordPress-timezone time. The current implementation is catalog-only: it does not enable Ozon checkout, rates, pickup selection or shipments.

0.137.3 fixes the follow-up Jet Logistic production validation blocker where `calc_transport` returned a non-currency `valuta` value together with a readable RUB `valuta_name`. Checkout and connection diagnostics now share the same parser precedence: `valuta_name` is authoritative, textual `valuta` is used only when the name is absent, numeric `valuta` is treated as provider metadata, and missing/numeric values fall back to the confirmed RUB Jet profile. Explicit non-RUB readable currency still blocks rates; diagnostics expose only safe `valuta` and `valuta_name` fields.

Pickup and courier production create/status/document/cancellation lifecycles, cancelled cleanup, and next-generation creation-attempt allocation have been verified for the supported RU physical-recipient scope.

Stable subsystems:

- core bootstrap and DI composition root;

- Ozon Delivery secure API foundation. The carrier/service key is `ozon_delivery`; it is a disabled builtin DeliveryService with initial `RU` country and generic service tabs, plus the `API Ozon` carrier tab. The current private application uses `client_credentials` with fixed code-owned scope `delivery-api.all`. Controlled live verification observed an absolute Unix-timestamp form of `expires_in`; tokens are therefore cached only as encrypted transient payloads until that confirmed expiry with a 60-second margin, and unknown expiry is never cached. `refresh_token` is intentionally ignored and never stored because refresh semantics remain unconfirmed. The explicit diagnostic always makes a fresh OAuth request and calls no application API method. No Ozon runtime rates, checkout, pickup points, shipments, statuses, cancellation, documents, or multi-box logic exists.

- Jet Logistic support through one carrier/service with separate geography import, two quote rates from one API calculation, manual tracking attach, status mappings, and shared autosync.
- PEK foundation and delivery-service settings. The built-in PEK service is disabled by default, stores legal sender data and the default Russian sender warehouse, preserves canonical branch timezone/availability fields, and declares supported-country capability for `RU`, `AM`, `BY`, `KG`, and `KZ`; administrators still choose the enabled subset through the existing service-country UI. PEK Shipment Framework verification has passed for the supported RU physical-recipient scope: pickup and courier create/status/documents/pre-acceptance cancellation are verified, cancellation false-negative reconciliation is handled, live cancelled-status integer `-3` is bounded to the cancelled-before-acceptance status, and fresh carrier-cancelled status automatically removes active PEK shipment storage after terminalizing the creation attempt. For `AM/BY/KG/KZ`, automatic create/cancel/document mutation workflows remain intentionally absent.
- PEK geography, destination pickup, quote foundation, and checkout runtime. `PekCarrier` is registered in `CarrierRegistry` while PEK automatic Shipment Framework creation remains RU-only. PEK calculation supports `RU -> RU/AM/BY/KG/KZ`, and the delivery service is still controlled by the existing service/country/admin enablement pipeline. The runtime reuses carrier-owned geography mappings, provider-backed destination terminals, and `PekQuoteService` to return `ПЭК до терминала` and `ПЭК курьером` rates without adding a PEK branch to `CheckoutOrchestrator`. Pickup quotes use a trusted selected `pek:pickup` warehouse when present, otherwise a preliminary suitable terminal chosen through the provider; after save, the selected warehouse ID becomes calculator `receiverWarehouseId`. A provider-valid terminal can still fail calculator pricing; this selected-terminal failure now triggers explicit recovery metadata on the current recovered rate, family-scoped clearing of only `pek:pickup`, a preliminary PEK recovery rate, preserved PEK method choice, and an inline transient method-level message asking for another terminal, without silently keeping the bad card or clearing other pickup families. That message is stripped before `wdc_platform_rates`, order meta, and calculation data persistence; the frontend keeps it only in current-page module memory across internal WooCommerce recalculations. Stale DOM/local selected-point state and POST save success do not clear the message: only authoritative post-calculation `/checkout/state` with a valid same-family selection does. Authoritative empty selections remove stale local points while preserving the message; destination, method-family, and reload still clear it. PEK public pickup REST uses nonce-protected registry-backed queries from production `rate_meta['pickup_provider_query']` stored on the session rate; `/points`, `/points/search`, and pickup save bootstrap the existing WooCommerce customer session before reading trusted rate context, distinguish `provider_session_unavailable` (503) from missing stored rate context (400), and still ignore browser cargo/location/address/coordinate data. Address-only `null/null` coordinate snapshots are accepted for canonical location IDs, malformed coordinate pairs fail closed, save validates only a point code through fresh `resolve_selection()`, stores a provider-owned destination fingerprint separately from the generic checkout destination fingerprint, and stale destination selections are cleared for PEK only. Free PEK points display as `Собственный пункт выдачи ПЭК`; paid points display as `Партнерский пункт выдачи ПЭК` with a possible surcharge warning, while internal warehouse UUIDs remain technical metadata. Courier quotes use location-level address plus coordinates only before a full address exists; full-address quotes omit canonical city coordinates. The final checkout base price uses `PekQuoteResult::price_kopecks`; saved calculation `api_base_price_rub` now stores this adjusted base, while PEK `costTotal` is preserved separately as `pek_carrier_base_price_rub`/`pek_carrier_price_kopecks`. Configured bag/plombing surcharges are formula comments before rules, not applied Rule Engine entries or rule delta. Quote cache keys include generic address/package/pickup-selection fingerprints and PEK’s safe context for selected terminal/provider fingerprint, full-address scope, request-scoped memoized planned datetime bucket, sender warehouse, hashed pricing identity, surcharge settings, and transport fields. No raw PEK request/response, credentials, client card, INN/KPP, or raw provider references are persisted in rates/session/order context.
- PEK quote/calculator diagnostics remain available for admin live checks. They use the same plannedDateTime resolver as checkout, continue to send documented `isHP=false` and `sealingPositionsCount=0`, and continue to separate carrier `costTotal` from store-owned light-cargo surcharges. Calculator response parsing, redaction, service breakdown typing, and user-scoped diagnostic storage are unchanged by checkout runtime.
- PEK schema integrity recovery. Migration `0050_repair_pek_foundation_schema.php` covers installed sites where migration history and physical schema drift apart, including the observed partial state where `wdc_pek_terminals` exists but `wdc_pek_location_mappings` is missing. The carrier-owned integrity service checks both PEK foundation tables with the current WordPress prefix, creates only absent tables through the existing repository installers, verifies postconditions before migration state can advance, and is idempotent on repeated update runs. The mapping table now uses physical `mapping_precision` to avoid the MySQL 8 reserved identifier `precision`; repository read/write code keeps the domain key `precision`, and migration `0051_migrate_pek_mapping_precision_column.php` non-destructively backfills `mapping_precision` from any legacy physical `` `precision` `` column. PEK installers check `$wpdb->last_error`, and migration boot reports failures through logging/admin notice instead of an unhandled site-wide fatal. Recovery does not perform destructive SQL, PEK API calls, canonical location writes, or runtime diagnostic DDL.

Recent fixes:

- CDEK now supports RU/AM/BY/KZ/KG through the existing service-country repository. Existing installs receive a one-time migration from empty/RU-only CDEK countries to the five-country default, while fresh installs seed the same defaults only when the built-in service is first created.
- DPD Geography imports AM/BY/KZ/KG locations into the shared locations table with `dpd_city_id` idempotency and without fake Russian identifiers. Foreign rows without GAR/FIAS use SQL `NULL` identity values in both single-save and bulk-upsert repository paths, ignore DPD foreign postcode/KLADR as canonical Russian fields, and reconcile the earlier malformed BY/Minsk row instead of requiring manual deletion. Foreign display names omit visual country-code prefixes while retaining `country_code` for identity and checkout filtering, and multiple existing exact foreign identity rows are resolved deterministically by current DPD mapping or lowest positive location id with `foreign_duplicate_identity_rows` diagnostics instead of creating more duplicates. Canonical, legacy, and DPD mapping lookups fail closed on SQL errors or invalid result shapes, so lookup failures become warning import row diagnostics instead of creating duplicate locations. Mapping finalization is transactional, preserves existing working mappings for conflict rows, skips stale cleanup on warning imports with row-level errors, reports logical changes separately from candidate count, and uses token-prefiltered PHP-normalized foreign identity rules in production SQL and in-memory smokes. Production finalization now splits candidate application into qualified UPDATE and INSERT SELECT statements, avoiding ambiguous `dpd_city_id` references from `INSERT ... SELECT ... ON DUPLICATE KEY UPDATE`. The serialized location index is built from fail-closed SQL pages before artifact creation, versioned, checksum-validated before each step, and separates own `fias_id` from contextual `city_fias_id` so a settlement's own FIAS cannot be shadowed by another row's city FIAS; the compact index stores only `own_fias`, `city_fias`, `kladr`, and `name`, while hierarchy metadata for own-FIAS ambiguity is loaded lazily for the candidate ids. Diagnostics now expose own-FIAS matches, city-FIAS fallback matches, hierarchy disambiguations, and true own-FIAS ambiguity separately. Page-query failures, corrupt indexes, and count SQL failures stop before destructive stale cleanup, public failure responses redact internal paths and index metadata, and rollback preserves working mappings. Browser import progress now separates read-only status polling from mutating locked step requests, caps browser steps at 500 rows, rejects stale offsets, and uses a self-scheduling runner without `setInterval`, so multiple tabs or slow foreign-row chunks cannot process the same CSV range concurrently. The import lock now uses atomic SQL compare-and-delete for expired takeover/release, protects start/step/reset, rejects failed jobs with saved artifacts until reset, blocks legacy runner-protocol jobs from automatic continuation, and keeps `state_revision` monotonic across jobs. Checkout location search now fetches direct own-name candidates before broad hierarchy candidates and orders direct candidates exact-before-prefix in production and in-memory paths, so exact BY Minsk is not hidden behind large Minsk-region result sets. Selected local DB checkout locations write only the own typed place into the visible WooCommerce city field while preserving region/district/canonical city metadata in hidden fields and session context; country changes clear destination city/state/postcode, local-location metadata, pickup selection, and cached quotes. CDEK city resolution is country-aware, supports manual city input, and does not persist CDEK city codes.
- CDEK shipment creation now handles international pickup and courier on the shared adapter/request/status/document pipeline. Non-RU courier uses raw WooCommerce address data plus resolved CDEK city code, and the CDEK-only optional recipient document field is visible from initial modal render for AM/BY/KZ/KG, maps to `recipient.tin` for KZ/KG or `recipient.passport_number` for AM/BY, and is never persisted or logged.
- CDEK pickup maps for manual EAEU cities reuse the resolved CDEK city code and fit the initial map viewport to loaded pickup point coordinates when no trusted destination coordinates exist. The derived viewport is never persisted as location data, physical user interaction cancels pending initial auto-fit, provider fit events no longer suppress the first subsequent user pan, explicit address/geolocation viewport actions refresh pickup points without being overridden by a later initial fit, and confirmed point selection cancels pending provider fit even when it does not focus the map.
- Checkout and order delivery recalculation now share a delivery lead-time pipeline: carrier raw lead time, shop processing calendar, optional carrier working-day conversion, delivery date rules, and final planned date. The global processing default is `2` shop working days, the per-service working-day flag defaults to off, and existing manual processing additions in rules should be removed manually where they are no longer wanted.
- The overview admin page now shows only platform information and delivery quote cache cleanup, while system requirements notices remain handled globally by `AdminNotices`.
- Checkout runtime gating now uses `CheckoutFeatureGate` with `enable_new_checkout_shipping` as the single source of truth; the legacy feature flag service was removed.
- Yandex Delivery shipment modal restores source drop-off PVZ presentation from the canonical V2 pickup context, including `full_address`, `schedule_text`, and coordinates, so the modal address and drop-off map survive the shipment framework flow.
- Shipment pickup picker defines its local `pickupContext()` resolver again, so Yandex source drop-off picker can open, run initial map search, and perform address search without a `ReferenceError`.
- Yandex cancellation polling toast treats `cancellation_started` lifecycle/poll flags as pending and no longer interprets the intermediate `carrier_status_title` as terminal failure.
- Yandex cancellation polling success toast now requires explicit cancellation confirmation via `cancelled_and_removed` or `yandex_status=CANCELLED`; empty `yandex_status` stays non-success.
- Yandex cancellation polling success now finalizes the existing progress toast by replacing it with a success message and auto-hiding it, so no persistent progress toast remains after cancellation.
- Shipment place analytics now refresh directly from current `shipment_item_rows` when item place assignment changes, so split rows are counted in their selected cargo places immediately.
- Yandex cancellation `cancelled_and_removed` now finalizes an existing cancellation progress toast even after the shipment UI has already been reset.
- Yandex terminal cancellation tick now treats the active cancellation toast state as lifecycle ownership, so missing terminal purpose metadata cannot leave the last progress toast visible.
- Yandex cancellation status AJAX now preserves the adapter's `cancelled_and_removed` marker in JSON, so terminal polling resets the shipment UI and finishes the cancellation toast instead of falling back to persistent progress.
- Shipment cost analytics now appears on `admin.php?page=wdc-platform`. It uses the `wdc_shipment_cost_analytics` materialized read-model table, indexes at most one matching created shipment per eligible order, uses `ShipmentBaseApiCostResolver`, canonical `actual_cost_*` fields, registry-driven carrier filters, integer 3% threshold checks, SQL sorting/pagination/aggregates, and no runtime WooCommerce order scan.
- PEK foundation now seeds a predefined disabled `pek` API delivery service with only `RU` on first setup and preserves administrator country choices on later boot, including an explicit empty selection. PEK settings store login, encrypted API key, legal sender data, client card, HTTP limits, SMS-release contractual limit, and the default sender warehouse snapshot including safe source (`free`, `nearest_cached_selection`, or `nearest_fresh_revalidation`). PEK admin POST actions execute through the carrier-owned admin component and PRG redirect back to the PEK tab; notices are user-scoped one-shot transients, not global settings. `/typesOfDelivery/all/` uses GET with JSON headers and no body; branch/legal/warehouse foundation methods use POST. Manual diagnostics run product, country, legal-form, and warehouse API checks independently, so a 403 from one reference endpoint does not interrupt the remaining read-only checks. Diagnostics expose `connection_ok`, `all_checks_passed`, endpoint, method, status, HTTP status, and public-safe messages; `/branches/all/` HTTP 200 confirms warehouse API availability without resaving the selected warehouse, while saved-ID semantic matching is reported separately as informational `warehouse_match` with safe counters and no raw response. A warehouse ID mismatch no longer means PEK explicitly rejected the ID and does not affect `all_checks_passed`. Machine `checked_at` datetimes are no longer masked as phones. Existing PEK pickup shipment preparation may also use an exact persisted checkout terminal selection when fresh destination nearestdepartments recheck is unavailable, but only with matching carrier/service/family, warehouse, branch, RU location, provider fingerprint, timestamp/source, availability, and local cargo limits; checkout terminal discovery still remains fail-closed and never uses stale lists. Unresolved timezone/date rows fail closed rather than falling back to `/branches/all/`. Shipment Framework remains unchanged.
