# Troubleshooting

For PEK shipment create failures, first check sender counterpart confirmation, PEK account login consistency, sender warehouse validity, RU-only destination, selected pickup terminal freshness, declared value limits, and SMS release availability. The confirmed counterpart API may return physical-person rows (`legalForm=3`) beside legal/IP rows; the plugin skips physical rows for sender matching and never stores/logs/renders their documents or PII, while private-token, counterpart API/logical, and response-contract failures have separate safe diagnostic stages. Sender warehouse preview failures should be diagnosed from safe `/branches/nearestdepartments/` validation fields: source (`nearest_cached_selection`, `nearest_fresh_revalidation`, or `shipment_modal_override`), warehouse ID hash, search address hash, free/paid counts, exact match count, constraints fingerprint/match, availability match, endpoint, HTTP status, and reason. Live 0.134.15 evidence proved `/branches/all/` can miss warehouse IDs freshly returned by nearestdepartments, so absence from `/branches/all/` is not a preview reject condition. If an alternate sender warehouse is selected in the modal, safe preview must show the alternate technical warehouse ID, source `shipment_modal_override`, and a different correlation hash from the default; otherwise the override source/UUID pair did not reach the server. Raw branch, warehouse rows, UUIDs, addresses, or PEK responses must not be logged. Courier preview/create may reject an order when persisted DaData no longer matches current Woo shipping fields, billing data would replace a distinct shipping destination, country is not current RU, explicit selected-location/city/settlement FIAS identifiers disagree, unit type data cannot prove corpus/structure/apartment/office/premise semantics, the saved address cannot prove street plus house, or `/branches/findzonebyaddress/` does not confirm the actual full courier address. Courier `near` precision is a warning, `bad` precision is a public address error, and malformed/missing zone context fails before SMS/private calls. PEK settings save is validate-before-write; invalid sender email, malformed sender phone, malformed recipient phone, or invalid bounded settings should leave the previous sender identity and counterpart snapshot unchanged. Status refresh failures from malformed PEK HTTP 200 payloads are not retried through basic fallback and must leave the saved shipment unchanged; valid basic fallback is only for explicit 403/404 and preserves expanded-only receiver/cost fields. A freshly-created PEK cargo may return live `cargoStatusId=-1`; treat only exact integer `-1` as "status ID not assigned yet", keep the valid `cargoStatus` string, omit `pek_cargo_status_id`, and reject any other negative or malformed ID. Uncertain transport/contract failures after submit are persisted as `pending_creation_in_carrier`; managers must verify the PEK cabinet and either manually attach the cargo code or remove the pending local attempt before retrying.

If sender warehouse preview fails after `POST /branches/nearestdepartments/` with HTTP 403, treat it as PEK method access denial/read-only API availability, not as proof that the warehouse ID is invalid. Picker search must preserve the previous server cache on failure and return controlled JSON. Shipment preview may continue only when the persisted sender warehouse snapshot exactly matches the requested warehouse ID, source is server-derived `free`, branch identity and original `checked_at` are present, and local cargo limits/availability still pass; preview includes a warning that earlier confirmed warehouse data is being used. Without that trusted snapshot, or when fresh HTTP 200 nearestdepartments does not return the exact warehouse, fail closed.

If PEK safe preview fails with `Не удалось подтвердить возможность выдачи груза по СМС.`, inspect the modal technical block `Проверка выдачи по СМС` and the underlying `sms_diagnostic` before changing payloads. The stage tells which read-only step failed: `sms_geography` for `/branches/checknocalcservices/`, `sms_private_token` for private-token acquisition, `sms_connected_services` for counterpart connected-services lookup, `sms_service_contract` for malformed service rows, `sms_limit_contract` for CODMaxSum parsing, and `sms_business_unavailable` for a valid business rejection such as missing SMS support or declared value above the confirmed limit. Safe diagnostics may include endpoint, method, HTTP status, error code, redacted PEK message, normalized field errors, response shape, and booleans/counts. They must not include private token, counterpart GUID, raw request/response, sender/receiver PII, credentials, or SMS cached fallback. Safe preview must still make zero `/preregistration/submit/` calls when SMS is not confirmed.

If PEK pickup safe preview fails before SMS with only `ПЭК отклонил доступ к методу.`, inspect the modal block `Подготовка заявки ПЭК` and `preparation_diagnostic`. A `destination_pickup` stage with `POST /branches/nearestdepartments/` means the selected terminal fresh recheck failed before SMS. Existing orders may continue only when the order already contains an exact server-validated PEK checkout selection with matching warehouse ID, branch ID, RU location, provider destination fingerprint, source, timestamp, availability, and local cargo limits; the preview then shows `pickup_destination_source=persisted_checkout_selection_access_fallback`, a fallback warning, and proceeds to SMS. Browser terminal fields, missing branch/fingerprint/location authority, fresh HTTP 200 negative results, and checkout terminal discovery all remain fail-closed.

If PEK `/preregistration/submit/` returns field errors for `cargos[0].services.*`, inspect the actual fake/live service object before changing receiver, SMS, or warehouse code. Version 0.135.5 fixes the confirmed missing required service objects by sending `hardPacking.enabled=false`, `strapping.enabled=false`, `documentsReturning.enabled=false`, pickup `delivery.enabled=false`, and courier `delivery.enabled=true` with `payer.type=1`. Disabled service blocks must not carry payer. `hardPacking` is PEK protective packing and must not be used for the shop light-cargo bag surcharge; `storing`, `bag`, `smallBag`, `packageType`, and `packagingType` remain absent.

After the first successful PEK submit, do not change receiver phone or planned handoff date behavior by guesswork. The plugin sends one receiver `personPhones[]` entry in documented `+7...` international form and does not send scalar receiver `phone`/`mobile` aliases; if the PEK cabinet displays both shortened and full phone forms, treat that as residual PEK-side presentation evidence until support clarifies otherwise. The preregistration payload currently does not send `common.plannedDate`, and safe preview exposes `planned_date_sent=false`; controlling PEK "Дата сдачи" needs a separate planned-date resolver with sender warehouse timezone, schedule, cutoff, weekends, and holidays.

If PEK cancellation returns "ПЭК не подтвердил отмену заявки" but the cabinet shows `Аннулировано до приемки груза`, do not press cancellation again. Version 0.135.7 treats the cancellation mutation as already sent and performs one fresh read-only status reconciliation; `Аннулировано до приемки груза` confirms success, terminalizes the attempt, and removes the active shipment from the order inside the cancellation flow. If the fresh status cannot be obtained, the outcome remains uncertain and the local shipment stays visible for reconciliation. Exact `cargoStatusId=-1` and `cargoStatusId="-1"` are live PEK sentinel compatibility forms. Version 0.135.8 also accepts integer `cargoStatusId=-3`, but only with `cargoStatus="Аннулировано до приемки груза"`; string `"-3"` and all other negative IDs remain invalid, and accepted sentinels are never persisted as `pek_cargo_status_id`. Version 0.135.9 also treats ordinary fresh status update to `CANCELLED` as authoritative terminal reconciliation: the existing attempt is terminalized and the active PEK shipment is removed without pressing cancellation again.

For Ozon pickup synchronization, inspect the `ПВЗ Ozon` tab. A failed generation does not replace the active catalog. The tab shows the active generation and its count; retry the manual update after resolving OAuth or transport failures. If the background step reports `pickup_lock_renew_failed`, inspect the Action Scheduler worker and the expired owner lock before starting a new import; the failed generation's partial points are removed while the previous active catalog remains. If no Ozon points are returned for a destination, first verify that the active snapshot exists and that the trusted checkout location has a complete coordinate pair; the provider deliberately does not infer a city from an address substring. The map, generic REST and provider do not call Ozon API. ## Ozon Delivery

If the Ozon OAuth diagnostic cannot obtain a token, verify Client ID, Client Secret, and the private application scope in the Ozon Delivery cabinet. The `API Ozon` tab shows only safe evidence: checked time, operation, HTTP status, scope, token type, known expiry, expiry time, source, code, message, Content-Type, JSON structure/key names, and bounded response size. It intentionally never shows raw response values, credentials, access tokens, refresh tokens, cookies, or headers.

If `Ozon до ПВЗ` is absent in checkout, first run the admin `Расчет Ozon` diagnostic on the Ozon tab. The runtime carrier stays disabled until credentials are complete, `Метод доставки Ozon` contains the official `shipment_method_id`, the local pickup snapshot has a valid destination point, and `POST /v1/order/checkout` succeeds for the same shipment method. Diagnostic output is safe only: status, endpoint, HTTP status, delivery total, insurance total, final price, currency, delivery days, point, package count, and bounded carrier error. It never renders raw request/response bodies. If the site shows a delivery-only Ozon price such as 109 RUB when the cabinet shows 109 RUB delivery plus 10 RUB insurance, verify that 0.141.18 or newer is deployed and that the quote cache context contains the insurance-aware Ozon pricing contract version.

If a multi-box Ozon cart disappears before any `/v1/order/checkout` request, verify that 0.141.18 or newer is deployed and inspect the safe diagnostic context before changing filters. Ozon packaging permits one parcel only when its rotated sides fit 50x50x30 cm. Larger compatible content must be split into multiple such parcels; an indivisible oversize item fails closed with `ozon_package_item_oversize` and no Ozon API request. For representative-point failures, the aggregate diagnostics remain available and contain no raw pickup rows, coordinates, phone, address, products, credentials, or Ozon request/response payloads.

After a successful Ozon calculation on 0.141.19 or newer, locate the single INFO record `Ozon Delivery checkout quote calculated.`. Its safe context contains `packages_count`, package weight and packing fields, up to 20 `places`, declared values, up to 20 normalized `postings`, and delivery/insurance/final totals. It must not contain phone, recipient, address, coordinates, product/SKU data, raw pickup/API payloads, tokens, or credentials.

For Ozon Shipment Framework create on 0.142.6 or newer, the manager-defined modal places are authoritative for `/v1/order/create`; checkout Packaging is only the buyer quote approximation. The create button becomes disabled with a busy label immediately after click while the server performs preflight checkout, create, approve, and one status enrichment. The pre-create checkout total is delivery plus insurance across all postings and is stored in the shared actual-cost fields with source detail `ozon_order_checkout_pre_create`. After successful approve the plugin performs one `posting/info` enrichment; if Ozon briefly still returns `CREATED` or the read fails, the completed create lifecycle remains at least `created_in_carrier` and later status sync can refresh raw Ozon statuses. Pickup shipments do not inherit courier recipient-address validation, and Ozon declared-value calculation uses the actual Shipment modal rows: quantity times unit price, grouped by place. Human external IDs sent to Ozon use the WooCommerce order number only, with `-1`, `-2`, etc. for multi-place postings; the stable UUID remains only in `Idempotency-Key`. Ozon action buttons use raw persisted `ozon_statuses[]`: `CREATED`, `FORMING`, and `READY_FOR_SHIPPING` allow `Отменить заказ`, while later, failed, cancelled, or unknown statuses expose local `Удалить заказ` and refresh. After cancel the plugin polls through the shared Shipment lifecycle every 5 seconds up to 14 attempts and removes the local shipment only when all postings are `CANCELED`; timeout leaves the shipment visible for a later update. Safe logs and persistence may contain internal shipment IDs, Ozon order/posting references, place counts, lifecycle tokens and normalized statuses, but never phone, recipient, address, raw API payloads, tokens, credentials, product names or SKU.

If the diagnostic is successful but checkout logs `ozon_representative_point_missing`, inspect the checkout city context. A canonical `selected_location_id` is sufficient even when session latitude/longitude are absent, but the corresponding active row in `wp_wdc_locations` must contain a valid latitude/longitude pair. Missing, inactive, invalid, or partial coordinates intentionally keep Ozon fail-closed.

If checkout logs `ozon_recipient_phone_missing`, verify that the standard WooCommerce `billing_phone` is present in the current checkout form. AJAX `woocommerce_update_order_review` is supported through decoded `post_data`, and direct `$_POST['billing_phone']` remains the non-AJAX fallback. Ozon can also use the optional `Резервный телефон для расчёта` setting only when the buyer phone is absent or cannot be normalized to `+7XXXXXXXXXX`; changing it does not reset the successful pricing live gate. Do not send phone values in logs or support tickets.

If `Ozon до ПВЗ` appears but the pickup map is empty, inspect the generic WDC pickup REST response. The Ozon rate must contain `rate_meta['pickup_provider_query']['destination_fingerprint']`, for example `country=RU|location_id=650000`; missing or empty fingerprints are correctly rejected as `provider_rate_context_missing`. If the response is successful but unexpectedly contains exactly 100 points for a large city, verify that the site is running 0.141.5 or newer: buyer lookup must not use first-N truncation and should return all eligible local Ozon points inside 60 km. If wp-admin reports unfinished migrations after deploying 0.141.4, deploy 0.141.5 so failed 0055 can rerun with the no-argument callback and create `active_geo_lookup`; no manual option edit is expected unless `0055_add_ozon_delivery_pickup_geo_lookup_index.php` was somehow marked applied despite the exception. Version 0.141.18 keeps the stable 0.141.13 Pickup Map open flow: after the bounded checkout context promise resolves, checkout creates the modal and immediately creates `WDCPickupMap`. The focused change is the generic `prefetch_points` capability. Ozon exposes `prefetch_points=false`, so checkout aborts/clears background point prefetch for Ozon and never passes cached `preloadedPoints` into its modal; the 60 km point dataset is fetched only when the buyer opens the map. Carriers without explicit `prefetch_points=false` keep historical prefetch behavior. Simple zoom/pan after the initial modal `/points` load should keep the fixed-area performance behavior. Do not bypass this by accepting browser coordinates, adding Ozon-specific REST/JS, or restoring a first-N point cap.

If `Ozon до ПВЗ` disappears after changing the city and the log shows `ozon_selected_point_stale`, verify that 0.141.6 or newer is deployed. Pickup selections are now filtered server-side by canonical `destination_fingerprint` before quote mapping, so a point selected for one location is removed before a quote for another location. The same selected point is still preserved for refreshes within the same canonical destination; if the point disappears from the active pickup snapshot for that same destination, the carrier stale-point error remains expected fail-closed behavior.

If a PEK courier or pickup create fails with a logical `/preregistration/submit/` validation error for `cargos[0].services.sealing`, verify that the site is running 0.135.10 or newer. Version 0.135.10 sends the `sealing` service object for every cargo: light cargo under the configured product-weight threshold sends `enabled=true` with sender payer, while non-sealed cargo sends exactly `enabled=false` and no payer. Do not fix this by enabling PEK `hardPacking`, adding a bag/package alias, matching quote service text, or changing SMS/receiver/courier address behavior.

If PEK status update fails with `ПЭК вернул некорректную дату статуса: deliveryPlanDate.`, do not change `common.plannedDate` or retry shipment creation. The successful courier create has already proven the preregistration payload; the failure is in read-only `/cargos/status/` DateTime normalization. Official PEK `/cargos/status/` documentation shows `deliveryPlanDate` as DateTime with example `2021-08-19T00:00:00`, while production returned `2026-08-19T22:23:16.833`. Version 0.135.11 accepts strict `Y-m-d\TH:i:s.v` only for `deliveryPlanDate`, preserves the original string, does not invent a timezone, and keeps safe diagnostic fields for future unsupported status dates: `field`, `value_type`, and a bounded scalar `value` when available. Do not broaden parsing with `strtotime()`, generic `DateTimeImmutable`, or by ignoring malformed present dates.

PEK universal status mapping is configurable in Delivery services -> PEK -> Статусы ПЭК. The table has separate columns for `ПЭК до терминала` and `ПЭК курьером`, including the delivery-type-specific default for `Прибыл` and the fixed pattern row `Выдан мест N из M`. These settings change WDC/order business status only. They do not change PEK raw status, cancellation eligibility, accepted-cargo protection, already-cancelled recognition, or automatic cancelled shipment cleanup.

If PEK courier preview reports that the courier delivery locality could not be restored, the failure happened before `/branches/findzonebyaddress/`: new orders should contain `rate_meta['location_id']`, while existing orders must have a valid persisted selected-location FIAS or, for older checkout records, a generic `_wdc_platform_city_fias_id` that maps to an active RU canonical location. A successful identity recovery should show `courier_location_identity_source=request_location_id` for new orders, `selected_location_fias_fallback` when selected-location FIAS exists, or `order_city_fias_fallback` for compatible historical orders, then `courier_branch_source=fresh_address_zone`.

Shipment create errors around creation attempts are framework lifecycle problems, not carrier payload problems. `shipment_create_in_progress` means the order plus carrier create lock is currently owned by another request or an invalid lock could not be safely reclaimed; wait and retry after the bounded lock TTL. Attempt-state restore errors mean `_wdc_shipment_creation_attempts` is malformed or contradicts the shipment evidence; do not submit externally until the order state is reviewed. Manual reconciliation should leave the same attempt active, while successful cancellation/local removal/pending discard should terminalize the old attempt before the shipment record disappears. The WordPress production lock backend requires both direct DB token-owned CAS and conservative object-cache reconciliation: after a successful conditional SQL delete, the individual non-autoload option cache is cleared and the lock key is removed from `notoptions`, leaving the next lookup to re-read DB rather than asserting absence. If create succeeds externally but then fails while moving the attempt to active/pending in the same request, inspect object-cache behavior before changing carrier payloads.

For a definite PEK `/preregistration/submit/` rejection, keep the public message broad (`ПЭК отклонил создание заявки.`) and inspect the admin-safe diagnostic block returned with the failed create response. It can contain only endpoint, method, HTTP status, failure stage, PEK error code/message, normalized field errors, and response shape. It must not contain raw request/response, receiver object, sender object, phone, email, INN, KPP, client card, private token, or credentials. A definite logical rejection does not create pending shipment and keeps the current creation attempt generation active for a corrected retry; uncertain transport/timeout/5xx/malformed-success cases remain pending/reconciliation-only.

If PEK safe preview and create do not show the same correlation hash, inspect the generic creation attempt state before carrier payloads. Explicit preview should reserve `creation_attempt_present=true` with a positive generation, repeated preview and the following create should reuse that generation, and a PEK mutation create without a valid generic `creation_attempt_id` must stop before `/preregistration/submit/`. After confirmed cancellation, external local removal, or uncertain pending removal, the old attempt should be terminal and the next explicit create should receive a new generation; validation-only failures before outbound submit should not create a new attempt. A `shipment_create_in_progress` error means the generic create lock prevented a duplicate AJAX mutation.

## PEK Schema Recovery

If PEK diagnostics report `PEK location mapping lookup failed`, first verify the physical tables with the active WordPress prefix:

```sql
SHOW TABLES LIKE 'wp_wdc_pek_location_mappings';
SHOW TABLES LIKE 'wp_wdc_pek_terminals';
SHOW COLUMNS FROM wp_wdc_pek_location_mappings LIKE 'mapping_precision';
```

Version 0.132.2 expects the physical mapping precision column to be `mapping_precision`; the domain/API mapping key remains `precision`. Migration `0050` repairs missing PEK foundation tables, and migration `0051` backfills `mapping_precision` from any legacy physical `` `precision` `` column. Failed migrations are not marked applied and `wdc_db_version` is not advanced; after fixing the DB issue, run the normal plugin update/migration lifecycle again. Do not create PEK tables from diagnostics or repository read/write methods.

For PEK destination terminal search failures after a successful location mapping, rerun the explicit admin diagnostic and read the structured report before changing contracts. The report separates `location_resolution` from destination terminal stages, shows stable `error_code`, `failure_stage`, endpoint, HTTP status, query fingerprint, preserved mapping fields, safe response shape for `/branches/nearestdepartments/`, aggregate rejection reason counters, and the redacted `api_error_message` when PEK returns a logical/API error object. When PEK returns field-level validation details under `error.fields`, the report shows them separately as `Ошибки полей ПЭК` with only normalized field names and redacted text messages. The `address` validation failure confirmed in 0.131.10 is fixed by sending a non-empty address on every destination terminal request; coordinate requests now contain both address and coordinates, while address-only requests omit coordinates. The stable `message` remains project-owned; the PEK detail is shown separately as "Ошибка ПЭК". Reports and logs intentionally do not store or display request bodies, headers, raw error objects, rejected/attempted field values, raw terminal rows, API keys, login, tokens, Basic Authorization blobs, or full raw responses. Failed explicit admin diagnostics also emit one project logger event with the same safe context so WooCommerce/debug logs have enough evidence for the next targeted fix.

For PEK calculator issues, use the closed admin quote diagnostic first, then compare checkout runtime only after the PEK delivery service is enabled. The diagnostic reports stable quote stage, endpoint/status, mode, mapping, safe request flags, insurance value, cargo conversion, store light-cargo surcharge policy, carrier cost, final adjusted cost, delivery days, safe service breakdown, safe response shape, and PEK field errors without storing raw request/response, INN/KPP/client card values, credentials, headers, addresses in logs, or stack traces. Checkout uses the same `PekQuoteService` through `PekCarrier`; pickup uses a preliminary provider-backed receiver warehouse until the customer selects a fresh-validated `pek:pickup` terminal, then checkout recalculates with the selected warehouse as calculator `receiverWarehouseId`. A terminal may pass provider validation but fail calculator pricing; in that case checkout should clear only `pek:pickup`, return a preliminary PEK rate, keep `pek:pickup` chosen, clear the selected card, and show `Не удалось рассчитать доставку в выбранный пункт ПЭК. Выберите другой пункт.` inside the affected shipping method, not as a global WooCommerce notice. The rejected-selection fields are transient one-calculation render metadata and should be absent from stored `wdc_platform_rates`, order `_wdc_platform_rate_meta`, and delivery calculation data after that render. The frontend keeps the visible inline message only in current-page memory so follow-up WooCommerce stabilization recalculations do not remove it. If the message disappears between recovery and the next stabilization update, verify that `syncPickupInlineNotices()` is not clearing by DOM/local `selectedPickupPoints`; success must come only from authoritative `/checkout/state` after the calculation. POST save 200 is provider/session success, not calculator success. Authoritative `pickup_selections={}` should delete stale local selection and keep the message; authoritative valid same-family selection clears it. Destination change, method change, or browser reload clears it, and no localStorage/sessionStorage/cookie/hidden field is used. If PEK disappears permanently or `active_pickup_family` moves to another carrier while a PEK selection remains in session, inspect the recovered rate for `pickup_selection_rejected=true` during the current calculation and verify `NewShippingMethod` cleared the rejected family in the same lifecycle. Saved calculation data should show PEK `api_base_price_rub` as the adjusted base before rules: carrier `costTotal` plus configured bag/plombing surcharge. The pure carrier amount is `pek_carrier_base_price_rub`/`pek_carrier_price_kopecks`. If the formula shows `Добавлен мешок и пломбировка`, that is a base adjustment note, not an entry in `applied_rules`; rule delta should be final price minus adjusted base. If PEK map loading returns `provider_session_unavailable`, WooCommerce did not expose a usable customer session to the REST request; check WooCommerce session cookies/bootstrap before inspecting stored rates. If it returns `provider_rate_context_missing`, the session was available but the selected stored rate context was absent or invalid: the production envelope should have top-level carrier/service/family/pickup flags and nested `rate_meta['pickup_provider_query']` with a non-empty `destination_fingerprint`. Saved PEK selections keep the provider SHA-256 in `provider_destination_fingerprint`; the generic checkout `destination_fingerprint` may be `country=RU|location_id=...` and must not be used as PEK provider authority. Address-only PEK mappings should store `latitude=null` and `longitude=null`; partial coordinates, empty strings, out-of-range values, or missing `service_key=pek` are invalid context. Browser address and coordinates are never trusted as a replacement for the canonical `location_id` mapping. Customer-facing PEK point cards should show `Собственный пункт выдачи ПЭК` or `Партнерский пункт выдачи ПЭК`, with the partner warning when applicable; warehouse UUIDs should appear only as technical point codes in metadata. Courier uses location-level provisional pricing until a full street/house or meaningful raw address exists, then sends full address without canonical city coordinates. If PEK pickup is selected without a valid terminal, checkout blocks with `Выберите терминал ПЭК.`.

If `ПЭК курьером` remains visible but `ПЭК до терминала` disappears, inspect the checkout PEK pickup mode diagnostic and Woo log entry for pickup preliminary options. A `/branches/nearestdepartments/` access/transport failure preserves `error_code` such as `pek_http_403`, endpoint, method, HTTP status, cache/source flags, and redacted PEK message; it is not mislabeled as a successful zero-terminal response. A successful HTTP 200 terminal response with no valid points still remains `pek_checkout_pickup_points_missing`. Checkout does not use stale terminal fail-open, and customer-facing checkout still only shows available shipping methods.
