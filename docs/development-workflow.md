# Development Workflow

Этот документ фиксирует обязательный процесс разработки Walls Delivery Calc. Он нужен, чтобы каждая задача проходила один и тот же цикл: от обсуждения до обновления документации и merge.

## 1. Обсуждение задачи

Перед началом разработки нужно зафиксировать:

- бизнес-цель задачи;
- затронутые пользовательские сценарии;
- ограничения WooCommerce, WordPress, HPOS, внешних API и окружения;
- документы из `docs/`, которые описывают текущую область;
- ожидаемый результат и критерии приемки.

Если задача меняет поведение checkout, доставки, ПВЗ, правил, календаря, адресов, отправлений или админки, это должно быть явно указано до создания ветки.

## 2. Выбор решения

До реализации нужно выбрать технический подход:

- какие модули будут изменены;
- какие данные будут добавлены или изменены;
- нужны ли миграции БД;
- нужны ли новые настройки;
- нужны ли фоновые задачи Action Scheduler / WP Cron;
- какие smoke-тесты или ручные проверки должны подтвердить результат;
- какие документы будут обновлены после завершения.

Решение должно опираться на существующую архитектуру `src/`, доменную модель, repositories, carrier adapters, Rule Engine, checkout runtime и HPOS-safe WooCommerce APIs.

## 3. Название ветки

Для каждой задачи выдается отдельная ветка от актуальной базовой ветки.

Формат:

```text
type/short-task-name
```

Примеры:

```text
feature/russian-post-shipments
feature/cdek-carrier-foundation
fix/pickup-selection-validation
chore/project-status
docs/development-roadmap
```

Ветка должна быть короткой, понятной и отражать основной результат задачи.

## 4. Промпт для Codex

Перед реализацией нужно подготовить промпт для Codex. Промпт должен содержать:

- текущую ветку;
- базовую ветку;
- ссылку на основной документ задачи в `docs/`;
- список дополнительных документов, которые нужно прочитать;
- точный список разрешенных изменений;
- список запрещенных изменений;
- ожидаемые проверки;
- требования к обновлению документации;
- нужно ли делать commit, push и PR.

Минимальный шаблон (с учетом того, что пользователь сам создает нужную ветку), выдается в формате md:

```text
Ветка: <branch-name>, мы уже в ней

Нужно реализовать <задача>.

Перед началом прочитай:
- docs/walls-delivery-calc-tech-spec.md
- docs/<relevant-doc>.md

Разрешено менять:
- <paths>

Нельзя менять:
- <paths или области>

После реализации:
- запусти <tests>
- обнови <docs>
- подготовь summary
```

## 5. Реализация

Во время реализации обязательно:

- работать только в ветке задачи;
- не менять несвязанные файлы;
- сохранять HPOS-safe работу с заказами через WooCommerce CRUD/API;
- использовать существующие сервисы, repositories, value objects и adapters;
- добавлять миграции только при изменении схемы данных;
- добавлять или обновлять smoke-тесты для затронутого поведения;
- не хранить секреты, raw API responses и временные файлы без явной debug/rotation стратегии.

## 6. Push ветки

После локальной проверки ветка не должна быть отправлена в удаленный репозиторий.
Нужно проверить:
- список измененных файлов;
- что изменения относятся только к задаче;
- что документация обновлена вместе с кодом.

Затем пользователь делает push самостоятельно.


## 7. Ревью кода

Ревью должно проверять:

- соответствие ТЗ и документам;
- корректность checkout/runtime поведения;
- HPOS compatibility;
- безопасность nonce/capability checks;
- устойчивость внешних API и fallback paths;
- миграции и обратную совместимость;
- достаточность тестов;
- актуальность документации.

Замечания ревью исправляются в той же ветке. После исправлений проверки повторяются.

## 8. Обновление документации

Документация обновляется в той же ветке, что и код. Нельзя завершать задачу, если код изменен, а соответствующие документы остались в старом состоянии.

Документы, которые должны рассматриваться при завершении каждой задачи:

- `docs/walls-delivery-calc-tech-spec.md` - если задача меняет общий продуктовый или архитектурный контракт;
- профильный документ области, например `docs/wdc-checkout-integration.md`, `docs/wdc-russian-post-domestic.md`, `docs/wdc-russian-post-pickup-points.md`, `docs/wdc-rule-engine-foundation.md`, `docs/wdc-delivery-calendar.md`;
- `docs/wdc-current-code-map.md` - если добавлены, удалены или существенно изменены модули;
- `docs/wdc-migration-plan.md` - если изменился порядок этапов, риски или стратегия перехода;
- `docs/todo.md` - если закрыт или появился технический остаток;
- `README.md` - если изменились runtime-требования, публичное поведение или важные команды проверки;
- `docs/project-status.md` - после его создания, при каждом изменении статуса готовности блоков.

## 9. Merge

Merge пользователем выполняется только после:

- завершенной реализации;
- успешных проверок;
- пройденного ревью;
- обновления документации;
- подтверждения, что ветка не содержит несвязанных изменений.

Для merge выдается текст PR на русском языке по сделанному в текущем шаге разработки.

## Рекомендация: docs/project-status.md

В документации сейчас есть технические документы по отдельным этапам, но нужен единый статусный документ. Рекомендуется создать `docs/project-status.md` и обновлять его после каждой завершенной задачи.

