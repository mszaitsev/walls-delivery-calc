# Development Workflow

Этот документ фиксирует обязательный процесс разработки Walls Delivery Calc.

Он нужен, чтобы каждая задача проходила один и тот же цикл:

```text
обсуждение
→ выбор решения
→ подготовка промпта
→ реализация
→ обновление документации
→ ревью
→ PR
→ merge
```

---

# 1. Обсуждение задачи

Перед началом разработки нужно зафиксировать:

* бизнес-цель задачи;
* затронутые пользовательские сценарии;
* ограничения WooCommerce, WordPress, HPOS, внешних API и окружения;
* документы из `docs/`, которые описывают текущую область;
* ожидаемый результат;
* критерии приемки.

Если задача меняет поведение:

* checkout;
* доставки;
* ПВЗ;
* правил;
* календаря;
* адресов;
* отправлений;
* административной части;

это должно быть явно указано до создания ветки.

---

# 2. Выбор решения

До реализации нужно выбрать технический подход.

Нужно определить:

* какие модули будут изменены;
* какие данные будут добавлены или изменены;
* нужны ли миграции БД;
* нужны ли новые настройки;
* нужны ли фоновые задачи Action Scheduler или WP Cron;
* какие smoke-тесты должны подтвердить результат;
* какие документы будут обновлены после завершения.

Решение должно опираться на существующую архитектуру:

* `src/`;
* domain model;
* repositories;
* carrier adapters;
* Rule Engine;
* checkout runtime;
* HPOS-safe WooCommerce APIs.

---

# 3. Использование tree.txt

В корне проекта находится:

```text
tree.txt
```

Он содержит актуальную структуру проекта:

```text
tree /a /F > tree.txt
```

После завершения каждой задачи Codex обязан обновлять:

```text
tree.txt
```

актуальным деревом проекта.

---

# 4. Название ветки

Для каждой задачи создается отдельная ветка.

Ветку создает пользователь самостоятельно.

Формат:

```text
type/short-task-name
```

Примеры:

```text
feature/russian-post-shipments
feature/order-status-mapping
feature/shipment-status-autosync

fix/pickup-selection-validation
fix/order-status-notes

chore/project-status
docs/development-roadmap
```

Название должно быть коротким и отражать основной результат задачи.

---

# 5. Промпт для Codex

Перед реализацией нужно подготовить промпт.

Промпт должен содержать:

* текущую ветку;
* версию плагина;
* основной документ области;
* дополнительные документы;
* список разрешенных изменений;
* список запрещенных изменений;
* список тестов;
* требования к документации;
* требования к version bump;
* указание не делать commit/push/PR.

Минимальный шаблон:

```text
Ветка: <branch-name>

Version:
<old> -> <new>

Перед началом прочитай:

- docs/<doc1>.md
- docs/<doc2>.md

Разрешено менять:

- <paths>

Нельзя менять:

- <paths>

После реализации:

- запусти <tests>
- обнови <docs>
- обнови tree.txt
- подготовь summary

Commit/push/PR не делать.
```

---

# 6. Versioning

Используется SemVer:

```text
MAJOR.MINOR.PATCH
```

Для проекта Walls Delivery Calc применяется следующий порядок.

## Новый крупный этап разработки

При создании новой функциональной ветки для нового этапа разработки увеличивается MINOR версия:

Примеры:

```text
0.38.2 -> 0.39.0
0.39.5 -> 0.40.0
0.40.7 -> 0.41.0
```

К таким этапам относятся:

* новые службы доставки;
* новые административные страницы;
* новые архитектурные блоки;
* новые интеграции;
* новые крупные пользовательские сценарии;
* существенные изменения бизнес-логики.

Обычно повышение MINOR версии происходит в первом промпте новой ветки.

---

## Продолжение работы внутри той же ветки

Каждый следующий промпт в рамках уже существующей ветки повышает PATCH версию.

Примеры:

```text
0.39.0 -> 0.39.1
0.39.1 -> 0.39.2
0.39.2 -> 0.39.3
```

Это правило действует независимо от размера доработки.

Даже если исправление маленькое:

* UI;
* CSS;
* текст;
* тест;
* документация;
* небольшая логика;

PATCH версия всё равно должна увеличиваться.

---

## Обязательное правило

Каждый промпт для Codex должен содержать:

```text
Version:
<текущая версия> -> <новая версия>
```

После завершения работы версия должна быть обновлена:

* в `walls-delivery-calc.php`;
* в связанных документах;
* в `docs/project-status.md`.

---

## Исключения

Версия может не изменяться только если задача не приводит к изменению кода проекта.

Примеры:

* обсуждение архитектуры;
* анализ документации;
* ревью кода;
* подготовка промпта;
* подготовка PR-текста.

Во всех остальных случаях version bump обязателен.

---

# 7. Реализация

Во время реализации обязательно:

* работать только в текущей ветке;
* не менять несвязанные файлы;
* использовать HPOS-safe WooCommerce APIs;
* использовать существующие сервисы, repositories и adapters;
* добавлять миграции только при изменении схемы данных;
* обновлять или добавлять smoke-тесты;
* не хранить секреты в коде;
* обновлять документацию вместе с кодом.

Все тексты интерфейса должны быть на русском языке:

* фронтенд;
* админка;
* сообщения;
* уведомления;
* названия кнопок;
* описания настроек.

---

# 8. Совместимость и миграции

Плагин пока не устанавливался на боевой сервер.

Заказы и реальные данные пользователей отсутствуют.

Поэтому внутри текущей ветки разработки допускается:

* менять структуру данных;
* менять подход к реализации;
* удалять устаревшие значения;
* не сохранять совместимость со старыми версиями текущей ветки.

То есть:

```text
Backward compatibility внутри текущей разработки обычно не требуется.
```

Исключение:

Нельзя без отдельного обсуждения ломать или удалять данные существующих инфраструктурных блоков:

* населенные пункты;
* ПВЗ;
* credentials;
* настройки служб доставки;
* справочники;
* другие уже реализованные службы доставки.

Например:

при разработке СДЭК нельзя менять таблицы или настройки Почты России без отдельного согласования.

Если требуется изменение уже существующей структуры другой службы доставки:

* сначала обсуждение;
* затем подтверждение;
* только после этого формируется промпт.

---

# 9. Push ветки

После локальной проверки:

* commit не делать;
* push не делать;
* PR не делать.

Нужно проверить:

* список измененных файлов;
* отсутствие лишних изменений;
* актуальность документации;
* актуальность tree.txt.

После этого пользователь самостоятельно делает push.

---

# 10. Ревью кода

Ревью должно проверять:

* соответствие ТЗ;
* соответствие документации;
* корректность runtime поведения;
* HPOS compatibility;
* безопасность nonce/capability checks;
* устойчивость внешних API;
* миграции;
* необходимость совместимости;
* достаточность тестов;
* актуальность документации;
* актуальность tree.txt.

Замечания исправляются в той же ветке.

После исправлений проверки повторяются.

---

# 11. Обновление документации

Документация обновляется в той же ветке, что и код.

Нельзя завершать задачу, если код изменен, а документация осталась старой.

Документы, которые нужно проверять при завершении задачи:

* `README.md`
* `docs/project-status.md`
* `docs/wdc-current-code-map.md`
* профильный документ области

Например:

```text
docs/wdc-russian-post-domestic.md
docs/wdc-russian-post-shipments.md
docs/wdc-russian-post-pickup-points.md
docs/wdc-delivery-services.md
docs/wdc-shipment-statuses.md
```

Если меняется архитектура:

обязательно обновлять:

```text
docs/wdc-current-code-map.md
```

Если появляется новый крупный блок:

создать новый профильный документ.

---

# 12. Ведение docs/project-status.md

Файл:

```text
docs/project-status.md
```

является главным источником информации о состоянии проекта.

После каждой завершенной задачи необходимо обновлять:

* реализованные блоки;
* текущую версию;
* roadmap;
* технический долг;
* следующий рекомендуемый этап;
* известные ограничения;
* несоответствия документации и кода.

Файл должен отражать актуальное состояние проекта на момент завершения задачи.

---

# 13. Технический долг и roadmap

Файл:

```text
docs/todo.md
```

больше не используется.

Источником информации о:

* техническом долге;
* незавершенных задачах;
* будущих этапах;
* roadmap;

является только:

```text
docs/project-status.md
```

Новые задачи должны добавляться туда.

---

# 14. Merge

Merge выполняется пользователем только после:

* завершенной реализации;
* успешных проверок;
* пройденного ревью;
* обновления документации;
* обновления tree.txt;
* отсутствия несвязанных изменений.

Для merge подготавливается:

* название PR;
* описание PR.

Все тексты PR должны быть на русском языке.

Описание должно содержать:

* версию;
* что реализовано;
* какие документы обновлены;
* какие тесты выполнены;
* что проверено вручную.

---

# 15. Итоговый отчет Codex

После завершения каждой задачи Codex обязан предоставить:

* новую версию;
* список измененных файлов;
* список обновленных документов;
* список выполненных тестов;
* краткое описание результата;
* подтверждение обновления tree.txt.

Формат:

```text
Version:
0.xx.x -> 0.yy.y

Что реализовано

Измененные файлы

Обновленные документы

Проверки выполнены

Commit/push/PR не делал.
```
