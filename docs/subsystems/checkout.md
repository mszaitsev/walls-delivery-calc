# Checkout

PEK checkout remains the source of trusted destination terminal selection for shipment creation. For PEK pickup shipments the saved `pek:pickup` point code is the receiver warehouse ID and is revalidated server-side for the current shipment cargo before submit; courier shipments use the WooCommerce shipping address and do not reuse city-center or terminal coordinates. Order meta persists DaData house, short/full house type, block, short/full block type, stead, stead type, flat, and short/full flat type fields for billing and shipping without a migration; old orders without these fields use the PEK conservative address fallback. Generic `_wdc_platform_city_fias_id` from server-side checkout city context is retained as city-level evidence for historical courier shipment identity recovery when numeric PEK rate `location_id` and selected-location FIAS are absent.

Version: 0.142.8

PEK calculation now supports the fixed sender-country matrix `RU -> RU`, `RU -> AM`, `RU -> BY`, `RU -> KG`, and `RU -> KZ`. The checkout runtime still uses the same PEK carrier/service/rate IDs (`pek:pickup`, `pek:courier`), same generic pickup map, same PEK own/partner point formatting, same selected-terminal repricing contract, and RUB `currencyCode=643`. Country code, canonical location ID, and provider destination fingerprint are part of trusted PEK metadata so same-text locations in different countries cannot share pickup selections or terminal cache entries. Unsupported directions, disabled service countries, missing canonical location identity, no pickup terminal, calculator rejection, malformed response, or non-RUB response omit only the affected PEK rate. A PEK `findzonebyaddress` unsupported/bad-precision mapping remains safe diagnostic evidence for checkout, but it is not a global pickup/courier blocker: pickup availability is proven by `/branches/nearestdepartments/` plus calculator `receiverWarehouseId`, and full-address courier availability is proven by the calculator.

PEK foreign checkout does not invoke SMS release, preregistration, cancellation, recipient document, tax/customs, or accompanying-documents services. The paid PEK "Сопроводительные документы" service remains disabled for international calculation.

Checkout code lives in `src/Checkout` and frontend assets in `assets/frontend`. It maps WooCommerce packages into `QuoteRequest`, runs carriers through `CheckoutOrchestrator`, applies rules, sorts rates, persists selected pickup/courier metadata, and validates checkout input.

`CheckoutFeatureGate` is the single runtime policy for enabling the new WooCommerce checkout shipping method and frontend runtime. Its source of truth is the `enable_new_checkout_shipping` setting from the platform settings page. The checkout debug panel uses the same gate and additionally requires `show_checkout_debug_panel`.

## Delivery Lead Time Pipeline

Checkout and order-admin recalculation use the same runtime order:

1. carrier raw lead time;
2. shop processing calendar;
3. carrier working-day conversion;
4. delivery date rules;
5. planned date.

Carrier adapters return the raw carrier `DateRange`. `DeliveryLeadTimeNormalizer` adds the global `shop_processing_working_days` setting, default `2`, using `CalendarTypes::SHOP`, then converts carrier working days through `CalendarTypes::CARRIER_RU` only when the service-level `delivery_days_are_working` checkbox is enabled. That checkbox defaults to `false`.

The current calculation day is not counted for shop processing, and the handoff day is not counted when carrier working days are converted. Rules run only after the base duration is normalized into calendar days. The planned date is calculated after rules from the final minimum delivery-days boundary, so checkout comments and order metadata stay aligned with rule changes.

## CDEK EAEU Availability

The `cdek` delivery service owns CDEK availability for `RU`, `AM`, `BY`, `KZ`, and `KG`. Administrators configure those countries with the existing service-country checkboxes, persisted in `wdc_delivery_service_countries`; the global service enabled flag remains independent. Checkout must not create a `cdek_international` service or bypass the delivery-service country selection.

CDEK city resolution uses the quote country, city, optional postcode, optional region for local disambiguation, RU FIAS when present, and coordinates when available. Manual city input is allowed, but a CDEK quote is produced only after an unambiguous exact normalized `/v2/location/cities` match. Ambiguous, missing, or null API city results suppress only the CDEK quote and must not block other carriers.

CDEK pickup and courier branches are available for every enabled CDEK country when the API returns a supported tariff. Delivery modes `1` and `3` map to courier; modes `2` and `4` map to pickup. Modes `6` through `10` may remain diagnostic data but are not checkout delivery types. Pickup requires at least one country- and city-matching CDEK handout point; courier does not depend on pickup points.

When a CDEK manual city has a resolved CDEK city code but no canonical location coordinates, the pickup map may load points directly by city code and fit the initial viewport to the returned point coordinates. That viewport is presentation-only: it is not saved as destination coordinates, city context, location identity, or shipment data. Programmatic initial viewport changes suppress only their own map event burst; the first later user pan or zoom must load points normally, and any physical user interaction cancels pending initial auto-fit for that modal instance. Explicit viewport actions such as address search, geolocation, selected-point focus, and confirmed point selection claim the viewport, cancel pending provider fit, and load or render points directly without waiting for suppressed map events.

Checkout location search builds its preliminary pool in two tiers: direct own-name candidates from `place_name`, `city_name`, and `settlement_name` are fetched before broader hierarchy/context candidates from region, district, city, place, and settlement fields. Direct candidates are ordered consistently in production SQL and in-memory smokes as exact own-name, then prefix own-name, then display name. The final ranking remains in PHP, but exact city/place matches such as BY Minsk cannot be cut off by a large region-only SQL result set before scoring. Country filtering remains part of the query and does not rely on visual display names.

When a local DB location is selected, the picker option remains contextual, for example `г Минск - Минский р-н, Минская область`, but the WooCommerce city field receives only the own typed place, for example `г Минск`. Region, district, city, and place canonical values are submitted through `wdc_platform_location_*` hidden fields and the checkout runtime stores `city_context.city_name` and `settlement_name` without hierarchy text, so CDEK receives `Минск` rather than `Минский р-н, г Минск`. Hidden selected-location country must match the posted checkout country; mismatches are ignored server-side.

Changing the actual destination country after initial checkout load clears the active destination scope's city, state, postcode, selected local-location hidden fields, selected notice, picker search state, pickup selection, and cached quote state through the existing checkout recalculation flow. A first load with an existing country and repeated same-country events do not clear fields.

Version 0.137.0 connects the PEK international calculation runtime to checkout for `RU -> RU/AM/BY/KG/KZ`. `PekCarrier` is registered in `CarrierRegistry` and returns the same two rates from one quote call: `ПЭК до терминала` and `ПЭК курьером`. The checkout orchestrator stays generic: service packaging still runs before carrier quote, PEK receives the packaged `QuoteRequest`, and no PEK branch is added to the orchestrator. Pickup pricing first uses a trusted selected terminal from `pickup_selections['pek:pickup']`; without a selection it obtains provider-backed suitable terminals from the PEK provider and uses the mapped main warehouse only when that warehouse is in the suitable set, otherwise a free point or first point. After a fresh terminal save the selected warehouse ID is the calculator `receiverWarehouseId`, so a partner/paid point can replace the preliminary price with a selected-terminal price. If an explicit selected terminal fails calculator pricing, PEK does not silently retain that terminal or use another terminal behind the selected card: the carrier returns a recovered preliminary rate with `pickup_selection_rejected` metadata, `NewShippingMethod` clears only the rejected family, keeps the recovered method selected, and the current shipping-method HTML renders `Не удалось рассчитать доставку в выбранный пункт ПЭК. Выберите другой пункт.` inside the PEK pickup block. This rejected-selection metadata is a one-calculation server event and is stripped before `wdc_platform_rates` session storage, order rate meta, and calculation data. The generic checkout frontend then keeps the inline message only in module memory for the current page so repeated WooCommerce `updated_checkout` DOM replacements do not erase it. Because local selection memory can be stale between recovery HTML and the following WooCommerce stabilization update, the message is not cleared by DOM hidden fields, `selectedPickupPoints`, or POST save success; it is cleared only after authoritative `/checkout/state` confirms a valid selected point for the same family/destination. Authoritative empty state replaces stale local selections and leaves the message visible. Courier quotes are provisional at location scope until a full street/house or meaningful raw address is present; full-address courier quotes send the address without canonical city coordinates because PEK coordinates take priority over address.

PEK pickup map access uses the existing public REST routes with a registry-backed trusted query bridge. Browser requests must provide nonce, shipping method id, and pickup family, but cargo, location, coordinates, radius, limit, address, and destination fingerprint come only from the server-stored production `rate_meta['pickup_provider_query']` metadata. Before registry-backed `/points`, `/points/search`, and checkout pickup save read that trusted context, the shared WooCommerce session bootstrapper ensures the current REST request has loaded the existing customer session created by checkout; it does not replace an existing session instance or accept rate context from the browser. Bootstrap failure returns `provider_session_unavailable` with HTTP 503, while a loaded session without the selected stored rate remains `provider_rate_context_missing` with HTTP 400. The top-level session rate envelope owns carrier/service/family/delivery-type flags and `requires_pickup_point`; the nested `rate_meta` block owns carrier-specific safe metadata. PEK trusted snapshots support both coordinate+address and address-only mappings: `latitude=null` plus `longitude=null` is valid when `location_id` is present, while partial, empty-string, non-numeric, non-finite, and out-of-range coordinate pairs are rejected. The full destination address is intentionally not stored in the session snapshot; the PEK provider uses `location_id` to reload the authoritative canonical mapping/address. Saving a PEK terminal trusts only point code, fresh-validates it through `resolve_selection()`, stores the result in the `pek:pickup` family with the server-owned `provider_destination_fingerprint`, and lets `CheckoutSessionManager` maintain the separate generic `destination_fingerprint` for broad stale-selection checks. Checkout POST cannot reconstruct a PEK selection from hidden fields alone; stale destination selections are cleared for the PEK family and checkout is blocked with `Выберите терминал ПЭК.`. PEK free points are presented as `Собственный пункт выдачи ПЭК`; paid points are presented as `Партнерский пункт выдачи ПЭК` with `Возможна небольшая доплата за доставку в этот пункт`. Internal PEK warehouse UUIDs remain technical point codes for pricing/order metadata, but customer-facing titles use the source-based presentation and not the UUID. `PekQuoteResult::price_kopecks` is the final pre-rules base price, including store light-cargo bag/plombing surcharges, and PEK stores that adjusted value in generic `api_base_price_rub`; the pure PEK `costTotal` remains available as `pek_carrier_base_price_rub` and `pek_carrier_price_kopecks`. The rule formula may show a store adjustment note for bag/plombing surcharges, including zero-price custom configurations, but those notes are not added to `applied_rules` and the rules price delta is measured from the adjusted base. Quote cache keys include generic destination/package/pickup-selection fingerprints plus PEK’s safe carrier context, including selected terminal and provider fingerprint, full-address fingerprint, planned datetime bucket, sender warehouse id, hashed contract-pricing identity, surcharge settings, product weight, and transport fields without raw credentials or counterpart identifiers. Planned datetime is memoized only for the current resolver instance so the cache context and calculator payload cannot drift at a 15-minute boundary.

## Canonical Requirements

- Rates are produced through WooCommerce shipping rates.
- A pickup delivery method does not automatically require a concrete pickup point. The canonical flag is `DeliveryRate::requires_pickup_point`; Jet Logistic returns a pickup rate with this flag disabled because Jet does not provide warehouse identifiers.
- The customer sees carrier, delivery type, delivery days/date, and final customer price.
- Pickup point UI appears only for pickup delivery methods.
- Courier address validation applies only when courier delivery is selected.
- Selected city, rate, tariff, pickup point, and courier address are preserved through checkout session/runtime state.
- Sorting can use price or delivery time.
- Manager recalculation in the order admin must save a clear order note with old/new delivery title and price.
- Planned checkout comments use `DeliveryRate::planned_delivery_comment` and the format `Доставка планируется* с 12 августа (среда).`.

Raw carrier quote responses are not order storage by default. Use diagnostics/logging for raw payloads and redact credentials.

Ozon Delivery registers one buyer-facing pickup rate, `ozon_delivery:pickup`, titled `Ozon до ПВЗ`. It is live-gated by the safe admin `Расчет Ozon` diagnostic and fails closed when credentials, `shipment_method_id`, active local pickup snapshot, trusted destination coordinates, representative/selected point, recipient phone, packaging, declared value, currency, or the official response contract are unavailable. Pricing uses official `POST /v1/order/checkout`: every expanded generic `PackagingParcel` quantity becomes an Ozon posting with one `dimensions` object in grams/millimeters and `declared_value` in RUB decimal amount. Ozon supports multiple postings in one checkout request, and the parser sums all successful `results[]` entries as `posting.estimated_delivery_cost + posting.estimated_insurance_cost`; both money objects must be RUB and malformed/missing insurance fails closed instead of being treated as zero. Delivery days are the maximum `posting.estimated_delivery_days`, and any posting-level Ozon error fails the whole quote. Declared value is sourced from `packaging.diagnostics['declared_value_rub']` with `QuoteRequest.order_total` fallback: one posting receives the full goods value, while multiple postings receive the same integer-safe whole-ruble `ceil(total goods value / posting_count)` amount. The recipient phone comes from canonical checkout context: `WooCommercePackageMapper` reads standard WooCommerce `billing_phone` from AJAX `post_data` first, then direct `$_POST['billing_phone']`, normalizes Russian numbers to `+7XXXXXXXXXX`, and does not copy raw checkout payload into `customer_context`. If that canonical field is empty or locally invalid, only Ozon may use its optional `Резервный телефон для расчёта` setting at request-build time; it never replaces a valid customer phone and is excluded from cache context, diagnostics, logs, and calculation metadata. Before point selection the carrier deterministically picks the nearest locally valid representative point; after explicit buyer selection it fresh-resolves the stable Ozon `point_id` through `OzonDeliveryPickupPointProvider::resolve_selection()` and reprices authoritatively for that point. The Ozon rate stores a canonical `pickup_provider_query` snapshot with non-empty `destination_fingerprint`, trusted 60 km radius, `reload_on_viewport_change=false`, and cargo `places` for each expanded posting, so generic pickup REST can validate the selected rate and call the local Ozon provider for map markers/cards. That reload capability is not part of mutable destination context: checkout localization exposes allowlisted `pickupRateCapabilities`, REST `/checkout/state` exposes authoritative `pickup_rate_capabilities`, JS stores them separately by normalized method id, and `openModal()` applies the active rate capability after destination/context reconciliation. The Ozon provider SQL first restricts to active generation, active rows, and coordinate bounds, then exact radius and cargo filters are applied; all eligible points inside 60 km are returned without a first-100/500 cutoff, while outside or cargo-incompatible points are excluded. Cargo compatibility is evaluated per place: point min/max weight is compared to the single posting weight, every place must fit, and dimensions are compared axis-correctly after sorting parcel sides and point limits to allow box rotation. Ozon points carry generic `requires_rate_refresh`, and the shared checkout JS uses that capability to trigger `update_checkout` after save without an Ozon branch. The fingerprint is destination-specific, stable for the same location, changes with the canonical destination, and excludes Ozon point ID, pickup generation, schedule, price, phone, token, and shipment method. The generic pickup map receives points only from the local provider through registry-backed REST, shows name/address/schedule, uses standard clustering, and does not expose technical point IDs. For fixed-area provider contexts the first `/points` response becomes the authoritative local dataset for the active modal instance; viewport changes after initial load do not trigger identical REST reloads, do not show `Поиск`/loading UI, do not set `aria-busy`, and do not rerender the full fixed-list sidebar, so sidebar scroll stays stable even after WooCommerce state refresh, selected-point repricing, destination changes, and modal reopen. Leaflet zoom reclustering remains coalesced, and the sidebar uses windowed rendering/search over the full source array instead of creating thousands of DOM rows. During real remote loads the same generic map lifecycle sets `aria-busy` on the map/list and shows `Загружаем пункты выдачи…` until the current REST response and marker/list rendering finish. Viewport-filtered local contexts can still rerender their list from the loaded dataset without showing remote loading.

Checkout `QuoteRequest.customer_context.destination_latitude/destination_longitude` are trusted server-side destination fields. `WooCommercePackageMapper` first uses existing complete coordinates from `selected_city` or `city_context`; when they are absent and `selected_location_id` is present, it loads the active canonical row from `LocationRepository::find_by_id()` and uses its valid latitude/longitude pair. It does not fuzzy-search by city name, parse addresses, trust browser coordinates, or save a fallback point. If the location row is missing, inactive, invalid, or has only one coordinate, both destination coordinates remain unresolved and carriers such as Ozon keep fail-closed preliminary quote behavior.

Do not change checkout UX or tariff business logic while working on shipment framework docs unless a confirmed defect requires it.

Ozon shipment creation deliberately does not reuse checkout Packaging. Checkout `PackagingBuilder` output is a pricing approximation for `POST /v1/order/checkout`; actual `POST /v1/order/create` uses only the Shipment modal's manager-confirmed places and item assignment data.
