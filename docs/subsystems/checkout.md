# Checkout

Version: 1.0.10

The WooCommerce checkout boundary maps the current package and canonical destination into a `QuoteRequest`, runs enabled carriers, applies rules and delivery-service post-processing, then publishes only fresh WDC rates. Package mapping is read-only: city selection/profile reconciliation own session mutations, and an active canonical location row is authoritative for identity and coordinates.

Rate sorting supports price and delivery-time modes. A deliberate sort-mode transition resets tariff/method choice once; ordinary recalculation preserves an available chosen WDC method, selected tariff, and same-destination pickup point. A changed canonical destination clears stale pickup state by family. Expected carrier no-match/empty outcomes are silent; technical failures follow the production logging policy.

Canonical RU checkout uses the WDC city picker and optional bounded DaData street/house suggestions. Manual or unsupported-country destinations retain the documented fallback behavior. Pickup REST state changes require the checkout nonce, provider/rate context is revalidated server-side, and the frontend supports both path-style and plain-permalink WordPress REST URLs.

PEK pickup and courier modes are calculated independently. Pickup requires a valid receiver terminal; courier uses the canonical delivery address and optional coordinates without depending on terminal discovery. A successful mode remains available if the other mode is unavailable.

## Delivery Lead Time Pipeline

Checkout and order-admin recalculation use the same runtime order:

1. carrier raw lead time;
2. shop processing calendar;
3. carrier working-day conversion;
4. delivery date rules;
5. planned date.

Carrier adapters return the raw carrier `DateRange`. `DeliveryLeadTimeNormalizer` asks `ShopProcessingDaysResolver` for the shop processing working-day count, then applies it through `CalendarTypes::SHOP`; fixed mode preserves the global `shop_processing_working_days` setting, default `2`. Dynamic mode uses `extra_processing_days + ceil(active_orders / orders_per_day)` from Delivery Services settings, where active orders are counted for selected canonical WooCommerce `wc-*` statuses through a cached HPOS-compatible `wc_get_orders()` paginated total query. After shop processing is normalized, carrier working days are converted through `CalendarTypes::CARRIER_RU` only when the service-level `delivery_days_are_working` checkbox is enabled. That checkbox defaults to `false`.

The current calculation day is not counted for shop processing, and the handoff day is not counted when carrier working days are converted. Rules run only after the base duration is normalized into calendar days. The planned date is calculated after rules from the final minimum delivery-days boundary, so checkout comments and order metadata stay aligned with rule changes.

## CDEK EAEU Availability

The `cdek` delivery service owns CDEK availability for `RU`, `AM`, `BY`, `KZ`, and `KG`. Administrators configure those countries with the existing service-country checkboxes, persisted in `wdc_delivery_service_countries`; the global service enabled flag remains independent. Checkout must not create a `cdek_international` service or bypass the delivery-service country selection.

CDEK city resolution uses the quote country, city, optional postcode, optional region for local disambiguation, RU FIAS when present, and coordinates when available. Manual city input is allowed, but a CDEK quote is produced only after an unambiguous exact normalized `/v2/location/cities` match. Ambiguous, missing, or null API city results suppress only the CDEK quote and must not block other carriers.

CDEK pickup and courier branches are available for every enabled CDEK country when the API returns a supported tariff. Delivery modes `1` and `3` map to courier; modes `2` and `4` map to pickup. Modes `6` through `10` may remain diagnostic data but are not checkout delivery types. Pickup requires at least one country- and city-matching CDEK handout point; courier does not depend on pickup points.

When a CDEK manual city has a resolved CDEK city code but no canonical location coordinates, the pickup map may load points directly by city code and fit the initial viewport to the returned point coordinates. That viewport is presentation-only: it is not saved as destination coordinates, city context, location identity, or shipment data. Programmatic initial viewport changes suppress only their own map event burst; the first later user pan or zoom must load points normally, and any physical user interaction cancels pending initial auto-fit for that modal instance. Explicit viewport actions such as address search, geolocation, selected-point focus, and confirmed point selection claim the viewport, cancel pending provider fit, and load or render points directly without waiting for suppressed map events.

Checkout location search builds its preliminary pool in two tiers: direct own-name candidates from `place_name`, `city_name`, and `settlement_name` are fetched before broader hierarchy/context candidates from region, district, city, place, and settlement fields. Direct candidates are ordered consistently in production SQL and in-memory smokes as exact own-name, then prefix own-name, then display name. The final ranking remains in PHP, but exact city/place matches such as BY Minsk cannot be cut off by a large region-only SQL result set before scoring. Country filtering remains part of the query and does not rely on visual display names.

When a local DB location is selected, the picker option remains contextual, for example `г Минск - Минский р-н, Минская область`, but the WooCommerce city field receives only the own typed place, for example `г Минск`. Region, district, city, and place canonical values are submitted through `wdc_platform_location_*` hidden fields and the checkout runtime stores `city_context.city_name` and `settlement_name` without hierarchy text, so CDEK receives `Минск` rather than `Минский р-н, г Минск`. Hidden selected-location country must match the posted checkout country; mismatches are ignored server-side.

Changing the actual destination country after initial checkout load clears the active destination scope's city, state, postcode, selected local-location hidden fields, selected notice, picker search state, pickup selection, and cached quote state through the existing checkout recalculation flow. A first load with an existing country and repeated same-country events do not clear fields.

PEK pickup map access uses the existing public REST routes with a registry-backed trusted query bridge. Browser requests must provide nonce, shipping method id, and pickup family, but cargo, location, coordinates, radius, limit, address, and destination fingerprint come only from the server-stored production `rate_meta['pickup_provider_query']` metadata. Before registry-backed `/points`, `/points/search`, and checkout pickup save read that trusted context, the shared WooCommerce session bootstrapper ensures the current REST request has loaded the existing customer session created by checkout; it does not replace an existing session instance or accept rate context from the browser. Bootstrap failure returns `provider_session_unavailable` with HTTP 503, while a loaded session without the selected stored rate remains `provider_rate_context_missing` with HTTP 400. The top-level session rate envelope owns carrier/service/family/delivery-type flags and `requires_pickup_point`; the nested `rate_meta` block owns carrier-specific safe metadata. PEK trusted snapshots support both coordinate+address and address-only mappings: `latitude=null` plus `longitude=null` is valid when `location_id` is present, while partial, empty-string, non-numeric, non-finite, and out-of-range coordinate pairs are rejected. The full destination address is intentionally not stored in the session snapshot; the PEK provider uses `location_id` to reload the authoritative canonical mapping/address. Saving a PEK terminal trusts only point code, fresh-validates it through `resolve_selection()`, stores the result in the `pek:pickup` family with the server-owned `provider_destination_fingerprint`, and lets `CheckoutSessionManager` maintain the separate generic `destination_fingerprint` for broad stale-selection checks. Checkout POST cannot reconstruct a PEK selection from hidden fields alone; stale destination selections are cleared for the PEK family and checkout is blocked with `Выберите терминал ПЭК.`. PEK free points are presented as `Собственный пункт выдачи ПЭК`; paid points are presented as `Партнерский пункт выдачи ПЭК` with `Возможна небольшая доплата за доставку в этот пункт`. Internal PEK warehouse UUIDs remain technical point codes for pricing/order metadata, but customer-facing titles use the source-based presentation and not the UUID. `PekQuoteResult::price_kopecks` is the final pre-rules base price, including store light-cargo bag/plombing surcharges, and PEK stores that adjusted value in generic `api_base_price_rub`; the pure PEK `costTotal` remains available as `pek_carrier_base_price_rub` and `pek_carrier_price_kopecks`. The rule formula may show a store adjustment note for bag/plombing surcharges, including zero-price custom configurations, but those notes are not added to `applied_rules` and the rules price delta is measured from the adjusted base. Quote cache keys include generic destination/package/pickup-selection fingerprints plus PEK’s safe carrier context, including selected terminal and provider fingerprint, full-address fingerprint, planned datetime bucket, sender warehouse id, hashed contract-pricing identity, surcharge settings, product weight, and transport fields without raw credentials or counterpart identifiers. Planned datetime is memoized only for the current resolver instance so the cache context and calculator payload cannot drift at a 15-minute boundary.

## Canonical Requirements

- Rates are produced through WooCommerce shipping rates.
- A pickup delivery method does not automatically require a concrete pickup point. The canonical flag is `DeliveryRate::requires_pickup_point`; Jet Logistic returns a pickup rate with this flag disabled because Jet does not provide warehouse identifiers.
- The customer sees carrier, delivery type, delivery days/date, and final customer price.
- Pickup point UI appears only for pickup delivery methods.
- Courier address validation applies only when courier delivery is selected.
- Selected city, rate, tariff, pickup point, and courier address are preserved through checkout session/runtime state. On reload, a coherent non-manual canonical session location is localized and restored into hidden checkout fields before textual profile reconciliation; mismatched IDs, country/city changes, and post-order cleanup do not restore stale identity. The location sentinel postcode `999999999` remains a storage/import value but is empty at checkout payload, resolver, visible-field, and selected-notice boundaries.
- Sorting can use price or delivery time.
- Manager recalculation in the order admin must save a clear order note with old/new delivery title and price.
- Planned checkout comments use `DeliveryRate::planned_delivery_comment` and the format `Доставка планируется* с 12 августа (среда).`.

Raw carrier quote responses are not order storage by default. Use diagnostics/logging for raw payloads and redact credentials.

Carrier-owned customer comments are appended through the generic post-rule extension point after service post-processing and planned-date enrichment. Ozon Delivery uses this to add exactly `Отслеживание посылки - в приложении Ozon, раздел Доставка` and `При отказе от посылки после её отправки покупатель оплачивает полную стоимость обратной доставки {s} руб.` to both `Ozon до ПВЗ` and `Ozon курьером`. The `{s}` value is `DeliveryRate::crossed_price ?? DeliveryRate::price`: promo shipping therefore uses the same amount shown as the checkout crossed price, while non-promo rates use the final customer shipping price. `WooCommerceRateMapper` keeps the existing `comments` pipeline for checkout rendering and also exposes carrier-owned `customer_comments` for authoritative order snapshot persistence. Pickup snapshots store these strings in `customer_comments`; courier orders store them in generic `_wdc_platform_customer_comments` and render them through the generic order/email delivery-comments display.

Ozon Delivery registers two buyer-facing rates: `ozon_delivery:pickup` titled `Ozon до ПВЗ` and `ozon_delivery:courier` titled `Ozon курьером`. Both are live-gated by credentials and the safe admin pricing diagnostic; pickup additionally requires the existing pickup `shipment_method_id`, while courier requires the separate courier `shipment_method_id`. Pricing uses official `POST /v1/order/checkout`: every expanded generic `PackagingParcel` quantity becomes an Ozon posting with one `dimensions` object in grams/millimeters and `declared_value` in RUB decimal amount. Pickup sends `delivery.delivery_point.delivery_point_id` from the local selected/representative point. Courier sends only `delivery.courier.coordinates.latitude/longitude` from `LocationRepository::find_by_id(selected_location_id)` after confirming the row is active, RU, has a valid non-zero latitude/longitude pair, and does not use pickup representative points, pickup limits, street/house coordinates, DaData suggestion coordinates, browser coordinate fields, customer-context coordinate aliases, or runtime geocoding fallback. The shared parser sums successful `results[]` entries as `posting.estimated_delivery_cost + posting.estimated_insurance_cost`; both money objects must be RUB and malformed/missing insurance fails closed. Delivery days are the maximum `posting.estimated_delivery_days`, and any posting-level Ozon error fails the affected quote. Courier parser/API failures keep the same carrier error code, but `OzonDeliveryCarrier` logs allowlisted diagnostics: location source/id/coordinates, shipment method, postings count, up to 20 posting dimension/declared-value rows, result counts, and safe `results[]` error fields. The recipient phone comes from canonical checkout context and the Ozon fallback phone remains excluded from cache context, diagnostics, logs, and calculation metadata. The pickup rate still stores the canonical `pickup_provider_query` snapshot for registry-backed map and selected-point repricing; the courier cache context includes only the authoritative courier pricing destination fingerprint: `location_id`, persisted latitude, and persisted longitude. Changing street, house, apartment, or postcode alone keeps the Ozon courier checkout cache context stable because those fields are not sent to `/v1/order/checkout`; changing `selected_location_id` changes the fingerprint and forces a fresh quote.

Order-admin delivery recalculation uses the selected recalculated rate as the source of pickup provider context. When a selected rate carries trusted `rate_meta['pickup_provider_query']`, the admin pickup search endpoint validates that snapshot against the current order destination and resolves points through `CarrierPickupPointProviderRegistry`; stale persisted selections from another family, such as an old Russian Post pickup point, cannot choose the provider for an Ozon recalculated rate. Reverse carrier switches use the same rule, and same-family selections may survive only through the existing fresh selection validation/reprice lifecycle.

Checkout `QuoteRequest.customer_context.destination_latitude/destination_longitude` are trusted server-side destination fields. `WooCommercePackageMapper` first uses existing complete coordinates from `selected_city` or `city_context`; when they are absent and `selected_location_id` is present, it loads the active canonical row from `LocationRepository::find_by_id()` and uses its valid latitude/longitude pair. It does not fuzzy-search by city name, parse addresses, trust browser coordinates, or save a fallback point. If the location row is missing, inactive, invalid, or has only one coordinate, both destination coordinates remain unresolved and carriers such as Ozon keep fail-closed preliminary quote behavior.

Do not change checkout UX or tariff business logic while working on shipment framework docs unless a confirmed defect requires it.

Ozon shipment creation deliberately does not reuse checkout Packaging. Checkout `PackagingBuilder` output is a pricing approximation for `POST /v1/order/checkout`; actual `POST /v1/order/create` uses only the Shipment modal's manager-confirmed places and item assignment data.
